# API Security: Common Mistakes and How to Avoid Them

**The most common serious API flaw is missing ownership checks: an endpoint verifies that a user is logged in, but not that the record they asked for is theirs.** OWASP lists it first in the [API Security Top 10 (2023)](https://api-security.owasp.org/editions/2023/en/0x11-t10) as **API1: Broken Object Level Authorization**. The governing rule behind it, and behind most of this guide: everything that arrives from a client is untrusted — even when your own app sent it.

> Written from an engineering perspective, not legal advice. Current as of November 2026.

This guide covers the mistakes we check for when building the backend behind a [mobile app](/en/services/mobile-apps) or [web application](/en/services/web-development), mapped to the OWASP list so your security reviewer can follow along.

---

## Why the app is not a line of defence

Anyone can inspect your app's traffic and see every request it sends and every response it gets back, with freely available tools.

**What this means:**
- **Hiding a button is not authorisation.** An attacker calls the API directly.
- **Validation in the app is not validation.** Repeat it on the server.
- **Any key inside the app is exposed.** Never ship secrets in client code.

---

## 1. Authentication and authorisation — the decisive difference

**Authentication:** who are you?
**Authorisation:** are you allowed to do this to *this specific record*?

```
GET /api/orders/12345
```

If the server only validates the token and returns order 12345 to any logged-in user, **any user can read everyone's orders** by changing the number. OWASP's [prevention advice for API1](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization) is to apply an authorisation check in **every function that uses client input to access a record**, and to write tests that try to bypass it.

Two related items on the same list:

- **API3: Broken Object Property Level Authorization** — the user may see the record, but not every field on it (an endpoint that lets a user update their own `role` field).
- **API5: Broken Function Level Authorization** — admin endpoints reachable by ordinary users because nobody checked the role.

---

## 2. Tokens — correct handling (API2: Broken Authentication)

**Store tokens in the platform's secure storage** — Keychain on iOS, Keystore on Android — not in ordinary preferences.

**Use two tokens:**
- **A short-lived access token** — minutes to an hour.
- **A longer-lived refresh token** — used to issue new access tokens.

A short access token narrows the damage window if it leaks.

**Provide revocation.** If a device is stolen or a compromise is suspected, you must be able to end one session or all of a user's sessions.

---

## 3. The most common mistakes in mobile backends

**1. Keys in the app bundle.** Anything in the bundle can be extracted. Sensitive keys stay on the server; the app calls your server, which calls the external service.

**2. Relying on client-side validation.** Client validation is for user experience; real validation happens on the server.

**3. Returning more data than needed.** An endpoint returns the full user object — email, phone, role — to display a name. Return what is displayed (this is API3 again).

**4. Revealing error messages.** "Wrong password" confirms the email is registered. Use one message: "invalid credentials".

**5. No rate limiting.** Without limits, login is brute-forceable and an SMS-code endpoint becomes someone else's free SMS gateway. OWASP files this under **API4: Unrestricted Resource Consumption** and **API6: Unrestricted Access to Sensitive Business Flows**.

**6. Sequential identifiers.** `/orders/1`, `/orders/2` invites enumeration. OWASP recommends random, unpredictable IDs such as GUIDs — **but ownership checks remain mandatory**; unguessable IDs only slow an attacker down.

**7. Forgotten endpoints.** Old versions, debug routes and staging hosts left reachable (**API9: Improper Inventory Management**). Keep a list of what is deployed, and retire what is not.

**8. Logging sensitive data.** Logs sometimes capture passwords, tokens or personal data. Logs are personal data too — see the [Saudi PDPL developer guide](/en/blog/pdpl-compliance-guide).

---

## 4. Input validation

**Validate every field on the server** — type, length, range, format.

**Do not trust hidden fields.** If the app sends `price` with an order, an attacker sends `price: 0`. **Calculate the price on the server** from the product ID.

**Use parameterised queries** — never build queries by string concatenation.

**Check uploaded files:** the real content type rather than the extension, a maximum size, and never serve them from an executable path.

**Validate URLs you fetch on the user's behalf.** A "fetch this image URL" feature can be turned against your internal network (**API7: Server Side Request Forgery**).

---

## 5. Transit and storage

**HTTPS on every connection,** without exception.

**Encrypt sensitive fields in the database** — do not rely on disk encryption alone.

**Hash passwords with a slow, purpose-built algorithm.** OWASP's [Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) recommends **Argon2id** first, **scrypt** if Argon2id is unavailable, and **bcrypt only for legacy systems**. It is explicit that fast hashes such as SHA-256 are not suitable, and that passwords should be hashed, not encrypted.

**Keep production and test environments separate,** and do not copy real customer data into development. Article 19 of Saudi Arabia's [PDPL](https://dgp.sdaia.gov.sa/wps/portal/pdp/knowledgecenter/details/PDPL) requires organisational, administrative and technical measures to protect personal data; whether a given test-data practice meets that is a question for your lawyer, but a production dump on a developer laptop is a security failure on any reading. Use generated or anonymised data instead.

---

## 6. Rate limiting and monitoring

**Rate-limit sensitive endpoints:** login, password reset, code sending, search, and anything that costs you money per call.

**Watch for:**
- Repeated failed logins from one source
- Requests for resources that do not belong to the user (enumeration)
- Sudden spikes in request rate

**Monitoring is a legal timing issue, not just good practice.** Under Article 24 of Saudi Arabia's [PDPL Implementing Regulation](https://dgp.sdaia.gov.sa/wps/portal/pdp/knowledgecenter/details/PDPL2), a controller must notify SDAIA within **72 hours of becoming aware** of a personal data breach that may cause harm, and notify affected users without undue delay. You cannot report on time a breach you have not detected.

---

## Pre-launch checklist

- [ ] Every endpoint checks **ownership** of the record, not just that someone is logged in (API1)
- [ ] Field-level checks on what a user may read or update (API3)
- [ ] Admin functions check the role (API5)
- [ ] Tokens in platform secure storage; short access token, refresh token, revocation
- [ ] No sensitive keys in the app bundle
- [ ] Server-side validation of every input; prices computed on the server
- [ ] Parameterised queries everywhere
- [ ] Outbound URL fetching restricted (API7)
- [ ] HTTPS everywhere
- [ ] Passwords hashed with Argon2id (or scrypt)
- [ ] Rate limits on login, reset, code sending and costly endpoints (API4, API6)
- [ ] Uniform error messages; responses return only displayed fields
- [ ] Inventory of deployed endpoints and versions; old ones retired (API9)
- [ ] Logs free of passwords, tokens and unnecessary personal data
- [ ] Monitoring that can surface a breach well inside 72 hours
- [ ] No production customer data in development or test

## Frequently asked questions

### What is Broken Object Level Authorization (BOLA)?

It is API1 in the OWASP API Security Top 10 (2023): an endpoint accepts a record ID from the client and returns or changes that record without checking that the logged-in user is allowed to. Any user can then reach another user's data by changing the ID. The fix is an ownership check in every function that uses client input to fetch a record.

### Do random IDs (UUIDs) fix BOLA?

No. OWASP recommends random, unpredictable IDs such as GUIDs because they make enumeration harder, but IDs leak through links, logs and shared screens. The authorisation check on every request is still required.

### Is bcrypt still acceptable for passwords in 2026?

Only for legacy systems. OWASP's Password Storage Cheat Sheet recommends Argon2id first and scrypt as the fallback, with bcrypt reserved for systems where neither is available. Fast hashes such as SHA-256 are not suitable for passwords.

### How do I keep third-party API keys out of a mobile app?

Do not put them in the app at all. The app calls your server, and your server calls the external service with the key. Anything inside the app bundle can be extracted by someone inspecting it.

### How fast must I report an API breach in Saudi Arabia?

If the breach involves personal data and may cause harm, Article 24 of the PDPL Implementing Regulation requires notifying SDAIA within 72 hours of becoming aware of it, and affected users without undue delay. If you do not have all the details within 72 hours, you provide them as soon as possible with reasons for the delay.

### Which endpoints need rate limiting first?

Login, password reset, verification-code sending, search, and any endpoint that costs you money per call such as SMS or AI requests. OWASP groups these risks under API4 (Unrestricted Resource Consumption) and API6 (Unrestricted Access to Sensitive Business Flows).

## Where to start

If you only fix one thing this week, make it API1: grep your backend for every route that takes an ID and confirm each one checks ownership. Then move secrets out of the app bundle and put rate limits on login and code sending. Those three changes close most of what attackers actually try first.
