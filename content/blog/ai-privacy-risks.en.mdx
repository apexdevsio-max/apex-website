# AI Privacy and Security Risks in Production

**The AI risks that actually reach production are three: prompt injection, retrieval that hands one user's data to another, and inputs being retained or trained on by the model provider.** All three are architectural. OWASP ranks prompt injection first in its [Top 10 for LLM applications (LLM01:2025)](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) and says it is unclear whether fool-proof prevention exists — so the real defence is limiting what the model can do.

> Written from an engineering perspective, not legal advice. Current as of November 2026.

This is the build-side view. For the legal obligations, see the [Gulf compliance guide](/en/blog/gulf-compliance-guide). If you are planning an assistant or document search over customer data, our [AI solutions](/en/services/ai-solutions) work starts from the controls below.

## Prompt injection

**What it is:** OWASP defines it as user prompts altering a model's behaviour or output in unintended ways. The harder variant is **indirect injection**, where the instructions arrive inside content the model reads — a website, a file — and may not even be visible to a person.

**Where untrusted content comes from** — more places than teams expect:

- User messages
- **Documents users upload** — CVs, invoices, support attachments
- **Web pages the system fetches**
- **Database fields users filled in** — a product review, a profile bio
- **Email bodies** in an automated processing flow

**What an injection attempts:** revealing your system prompt, ignoring your restrictions, extracting data from the context, or — most damaging — triggering a tool the model can call.

**What actually reduces the risk** (these line up with OWASP's own mitigations):

**Least privilege on tools.** OWASP's advice is to give the model only the access it needs and keep privileged functions in application code. If the model can only read, injection cannot make it write. **Ask what the worst instruction the model could follow would do, then remove that capability.**

**Human approval for high-risk actions.** Anything that sends, pays, deletes or changes permissions waits for a person. A silent compromise becomes a visible request.

**Treat model output as untrusted input.** Validate it against the format you expect before it reaches another system. Output rendered as HTML without escaping is a cross-site scripting route.

**Separate untrusted content from instructions** using whatever structure your provider offers, and never build prompts by pasting user text into instruction text.

**Test adversarially, on a schedule.** Try to break your own assistant with hostile documents before someone else does.

> **The realistic posture:** assume an injection will eventually succeed, and make sure a successful one cannot do anything expensive. A model that lacks a dangerous capability cannot be tricked into using it.

## Data leakage between users

The failure that ends internal AI projects is almost always a retrieval bug rather than a model failure.

**How it happens:** a shared vector index without per-user filtering. User A asks a question, retrieval returns the closest passages, and one came from User B's document. The model summarises it faithfully.

**The prevention is architectural:**

- **Filter at retrieval, never at generation.** Exclude documents the user cannot access *before* the model sees them. Telling the model to withhold information is a suggestion to a probabilistic system.
- **Check permissions at query time**, not indexing time, so revoked access takes effect immediately.
- **Test it.** Create two accounts with distinct documents and deliberately try to retrieve one from the other.

**Conversation history is the same class of problem.** A shared cache or a mis-scoped session key surfaces one user's history to another. Scope every cache key to the user.

## Retention and training: check the tier, not the brand

Whether your inputs are kept or trained on is set by the product tier and its terms, not by the model's name. As of November 2026, the providers' own documentation says:

| Provider and tier | Used for training? | Retention noted by the provider |
|---|---|---|
| [OpenAI API](https://developers.openai.com/api/docs/guides/your-data) | No, unless you explicitly opt in | Abuse-monitoring logs kept up to 30 days by default; Zero Data Retention for approved customers |
| [Google Gemini API](https://aistudio.google.com/docs/terms) — unpaid | Content used to "provide, improve, and develop" products; human reviewers may read it | Google says not to submit sensitive, confidential or personal information |
| Google Gemini API — paid | No | Prompts and responses logged for a limited period for abuse detection |
| [Anthropic](https://www.anthropic.com/news/updates-to-our-consumer-terms) consumer (Free, Pro, Max) | Only if the user allows it (change announced 28 August 2025) | Five years if allowed; 30 days otherwise |
| Anthropic API and commercial plans | The consumer change does not apply | Governed by commercial terms |

**The pattern to watch for:** a developer prototypes on a free or personal account, the prototype becomes the production integration, and nobody re-reads the terms. With the Gemini API that difference is the line between "do not send personal data" and "not used to improve products". Check which key and which tier your production system actually uses.

**Where inference runs matters too.** Sending a Saudi user's personal data to a model hosted abroad is a transfer outside the Kingdom. SDAIA's [transfer regulation](https://dgp.sdaia.gov.sa/wps/portal/pdp/knowledgecenter/details/RegulationonPersonalDataTransferOutsidetheKingdom) allows transfers to countries on its adequacy list or under safeguards such as standard contractual clauses, and requires a documented risk assessment when sensitive data is transferred or data moves continuously or at large scale (Article 7). A support assistant sending every chat abroad is plausibly "continuous". Ask your lawyer which basis your setup relies on; see [data residency in the Gulf](/en/blog/data-residency-gulf) for the architecture side.

**Log what you send.** You cannot answer "what data went to which provider" after the fact without it — and that is the first question in an incident or a procurement review.

## What you are storing

**Conversation logs** contain whatever users typed, and users type things you did not ask for — ID numbers, medical details, passwords. Apply the same retention rules as any personal data, and redact obvious patterns before storage.

**Vector embeddings are not anonymous.** [Morris et al. (2023)](https://arxiv.org/abs/2310.06816) recovered 92% of 32-token text inputs exactly from their embeddings. Treat your vector database as containing the source text — including for residency and deletion.

**Provider-side storage features** — stored conversations, files, assistants — keep data on the provider's side for longer than a single request. OpenAI's documentation, for example, lists Conversations, Assistants, Files and Fine-tuning among endpoints not eligible for Zero Data Retention. Know which features you use.

**Debug traces** are the quiet one. Logging full prompts for troubleshooting often sends them to a third-party logging service in another country — another transfer nobody documented.

## Controls worth building

Ordered by value relative to effort:

1. **Minimise what you send.** Redact identifiers before they reach the model. A support assistant rarely needs the full customer record to answer a returns question.
2. **Constrain tool capability.** Read-only wherever possible; human approval for anything consequential.
3. **Filter retrieval by user.** A hard constraint, checked at query time.
4. **Use the right tier.** Production keys on a paid or enterprise tier whose terms you have read.
5. **Log requests, not content.** Record that a request happened, its size and which feature made it — without storing the text where possible.
6. **Rate-limit per user.** It bounds both cost and bulk-extraction attempts.
7. **Monitor for anomalies.** A spike in requests or token use usually means a bug or abuse; catch it in hours, not at invoice time.

## Frequently asked questions

### Can prompt injection be fully prevented?

No one can promise that. OWASP's LLM01:2025 entry says it is unclear whether fool-proof prevention exists and that mitigations reduce impact. Design so a successful injection cannot do damage: least-privilege tools, human approval for high-risk actions, and validation of model output.

### Does the OpenAI API train on my customers' data?

Not by default. OpenAI's API documentation says data sent to the API is not used to train or improve its models unless you explicitly opt in. Abuse-monitoring logs are kept for up to 30 days by default, and approved customers can get Zero Data Retention.

### Is the free Gemini API safe for personal data?

Google's own terms say no. For unpaid services, Google may use submitted content to improve its products, human reviewers may read it, and the terms say not to submit sensitive, confidential or personal information. On paid services, Google says it does not use prompts or responses to improve its products.

### Are vector embeddings anonymous?

No. A 2023 study by Morris and colleagues recovered 92% of 32-token inputs exactly from their embeddings. Treat a vector database as holding the original text for retention, deletion and data residency purposes.

### Is calling a foreign AI API a cross-border transfer under Saudi PDPL?

If the request contains personal data and the model runs outside the Kingdom, treat it as one. SDAIA's transfer regulation permits transfers under adequacy or safeguards such as standard contractual clauses, and requires a risk assessment for sensitive data or continuous or large-scale transfers. Confirm the basis for your setup with counsel.

### How do I stop a RAG assistant leaking documents between users?

Filter by the user's permissions at retrieval time, before anything reaches the model, and check those permissions at query time rather than at indexing time. Then test it with two accounts holding different documents and try to retrieve one from the other.

## Settle it before you integrate

Assume injection will succeed and limit what it could do. Filter retrieval by user with a hard constraint. And read the retention and training terms of the exact tier you will run in production before the first real customer message goes through it.
