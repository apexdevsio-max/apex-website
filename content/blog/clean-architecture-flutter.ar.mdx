# معمارية Clean Architecture في Flutter: متى تستحق تعقيدها؟

**معمارية Clean Architecture تستحق تكلفتها في تطبيق Flutter فيه منطق عمل حقيقي، ويعمل عليه أكثر من مطوّر، ويُتوقَّع أن يعيش سنوات. أما في MVP أو تطبيق من خمس شاشات يعرض بيانات فقط، فهي مبالغة.** و[دليل المعمارية الرسمي من Flutter](https://docs.flutter.dev/app-architecture/guide) يقف الموقف نفسه: طبقتا الواجهة والبيانات إلزاميتان، وطبقة المجال بحالات الاستخدام اختيارية تُضاف «عند الحاجة فقط».

المعمارية من أكثر ما يُناقَش في مجتمع Flutter، ومن أكثر ما يُطبَّق في غير مكانه. مشاريع كثيرة تتبنّاها لأنها «الممارسة الصحيحة» فتنتهي بعشرة ملفات لعرض قائمة بسيطة. في هذا الدليل: الطبقات، وما يضيفه توجيه Flutter الرسمي، وكيف تعرف في أي جهة يقع مشروعك.

---

## المشكلة التي تحلها

بلا معمارية واضحة، ينتهي المشروع بملفات واجهة تحوي كل شيء: استدعاءات الشبكة، ومنطق العمل، وتحويل البيانات، وإدارة الحالة، وأحياناً في ملف واحد بألف سطر.

**النتائج المتوقعة:**
- **الاختبار شبه مستحيل**، لأنك لا تستطيع اختبار المنطق دون بناء الواجهة.
- **التغيير مكلف**: تبديل مصدر البيانات يعني تعديل كل شاشة.
- **إعادة الاستخدام تختفي**، فيتكرر المنطق نفسه في خمسة أماكن.

المعمارية تحل هذا بفصل المسؤوليات في طبقات لكل منها دور واحد. وتوثيق Flutter يسمّي الفكرة نفسها [فصل الاهتمامات](https://docs.flutter.dev/app-architecture/concepts): منطق الواجهة منفصل عن منطق العمل، وكل طبقة لا تتواصل إلا مع الطبقة التي فوقها أو تحتها مباشرة.

---

## الطبقات الثلاث

### 1. طبقة العرض (Presentation)

الواجهات وإدارة الحالة. **مسؤوليتها الوحيدة:** عرض ما تتلقاه واستقبال تفاعل المستخدم.

**لا تحوي** استدعاءات شبكة، ولا منطق عمل، ولا معرفة بمصدر البيانات.

### 2. طبقة المجال (Domain)

**منطق العمل نفسه**، وهي الطبقة الوحيدة التي **لا تعتمد على أي شيء خارجي**: لا Flutter ولا قاعدة بيانات ولا شبكة.

تحوي الكيانات (نماذج العمل)، وحالات الاستخدام (Use Cases)، وواجهات المستودعات (عقود مجرّدة).

**هذا الاستقلال هو الفائدة الحقيقية:** منطق عملك قابل للاختبار بلا أي بنية تحتية.

### 3. طبقة البيانات (Data)

التنفيذ الفعلي: استدعاءات الـAPI، وقاعدة البيانات المحلية، والتخزين المؤقت. تنفّذ العقود التي عرّفتها طبقة المجال.

---

## كيف تقابل هذه الطبقات دليل Flutter الرسمي؟

فريق Flutter ينشر بنية موصى بها، وهي أخف من Clean Architecture بصيغتها الكاملة. معرفة الاثنتين تساعدك على اختيار الوزن المناسب لمشروعك.

| دليل Flutter | المكوّنات | إلزامية؟ |
|---|---|---|
| طبقة الواجهة | العروض (Widgets) ونماذج العرض (View Models) | نعم |
| طبقة المجال | حالات الاستخدام (وتُسمّى Interactors) | **اختيارية** |
| طبقة البيانات | المستودعات (المصدر الوحيد للحقيقة) والخدمات (أغلفة للـAPI والملفات المحلية وواجهات المنصة) | نعم |

ويرى الدليل أن حالات الاستخدام تستحق الإضافة حين يكون المنطق:

1. يدمج بيانات من عدة مستودعات،
2. أو معقداً جداً،
3. أو تعيد استخدامه عدة نماذج عرض.

وفيما عدا ذلك يتحدث نموذج العرض مع المستودع مباشرة. والدليل صريح في ذكر التكلفة أيضاً: حالات الاستخدام تضيف أصنافاً وكوداً متكرراً وكائنات محاكاة (Mocks) إضافية في الاختبارات. وهذه هي المقايضة نفسها التي يدور حولها هذا المقال، بلسان من يطوّرون الإطار.

## قاعدة الاعتماد: أساس كل شيء

**الاعتماد يتجه للداخل دائماً.** في [مقال روبرت مارتن عام 2012](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html) نص القاعدة: اعتماديات الكود المصدري لا يمكن أن تتجه إلا للداخل.

```
العرض ──► المجال ◄── البيانات
```

طبقة العرض تعرف المجال. طبقة البيانات تعرف المجال. **والمجال لا يعرف أياً منهما.**

**لماذا هذا مهم؟** لأن تبديل مصدر البيانات (من API إلى قاعدة محلية) أو تبديل إطار الواجهة **لا يمس منطق عملك إطلاقاً**. ويذكر مقال مارتن أيضاً أن عدد الدوائر توضيحي وليس محصوراً في أربع، وهذا تذكير مفيد بأن عدد الطبقات يتبع المشروع لا العكس.

## مثال عملي مبسّط

```dart
// المجال: كيان — لا يعرف شيئاً عن الشبكة أو Flutter
class Lesson {
  final String id;
  final String title;
  final bool isCompleted;
  const Lesson({required this.id, required this.title, required this.isCompleted});
}

// المجال: عقد مجرّد
abstract class LessonRepository {
  Future<List<Lesson>> getLessons(String courseId);
}

// المجال: حالة استخدام
class GetCourseLessons {
  final LessonRepository repository;
  const GetCourseLessons(this.repository);

  Future<List<Lesson>> call(String courseId) => repository.getLessons(courseId);
}

// البيانات: التنفيذ الفعلي
class LessonRepositoryImpl implements LessonRepository {
  final ApiClient api;
  final LocalCache cache;
  const LessonRepositoryImpl(this.api, this.cache);

  @override
  Future<List<Lesson>> getLessons(String courseId) async {
    final cached = await cache.getLessons(courseId);
    if (cached != null) return cached;
    final result = await api.fetchLessons(courseId);
    await cache.saveLessons(courseId, result);
    return result;
  }
}
```

**لاحظ:** حالة الاستخدام لا تعرف أن هناك تخزيناً مؤقتاً أصلاً، فيمكنك تغيير استراتيجية التخزين دون لمس المنطق. ولاحظ أيضاً أن `GetCourseLessons` مجرد تمرير؛ وبمعايير Flutter نفسها لا تستحق مكانها ما لم يُضَف إليها منطق لاحقاً (راجع «أخطاء التطبيق الشائعة» أدناه).

## مثال حقيقي: تطبيق «تفوقي»

مثالنا المنشور على هذه البنية هو [تطبيق «تفوقي»](/ar/portfolio/tafawwoq-educational-app)، تطبيق تعليمي عربي للمراهقين مبني بـFlutter ومعمارية Clean Architecture، مع BLoC لإدارة الحالة وواجهة عربية RTL كاملة. نظام الاختبارات فيه يعمل بمؤقت زمني وتصحيح آلي. وفصل طبقة المجال عن الواجهة والبيانات هو ما جعل منطق الاختبارات والتقييم قابلاً للاختبار بمعزل عن الواجهة، وهذا مهم في منتج تُحسب فيه الدرجات.

والتطبيق يطابق قائمة «تستحق» أدناه: عدة أنظمة مترابطة (دروس واختبارات واشتراكات)، ومنطق يظهر خطؤه للمستخدم مباشرة، ومنتج يُراد له أن يُصان لا أن يُرمى. إن كنت تخطط لتطبيق من هذا النوع، فـ[خدمة تطوير تطبيقات الجوال](/ar/services/mobile-apps) تشمل اختيار المعمارية ضمن البناء.

## متى تستحق؟ ومتى تكون مبالغة؟

هذا القسم أهم من الشرح التقني، لأن الخطأ الشائع ليس تطبيق المعمارية بشكل خاطئ، بل **تطبيقها حيث لا تلزم**.

### تستحق حين:

- **التطبيق كبير**: عشرات الشاشات ومنطق عمل حقيقي.
- **يعمل عليه أكثر من مطوّر**، فالطبقات تحدد المسؤوليات وتقلّل التعارض.
- **العمر المتوقع طويل**: سنوات من التطوير والصيانة.
- **الاختبار مهم**: قطاع منظَّم أو منطق يحسب مبالغ أو درجات.
- **مصادر البيانات قد تتغير**، أو تحتاج إلى العمل دون اتصال.

### تكون مبالغة حين:

- **التطبيق MVP لاختبار فكرة.** راجع [دليل MVP](/ar/blog/mvp-vs-full-product)؛ السرعة هنا أهم من البنية.
- **التطبيق صغير**: خمس شاشات تعرض بيانات بلا منطق يُذكر.
- **مطوّر واحد على مشروع قصير**، فالعبء أعلى من الفائدة.
- **نموذج أولي** سيُرمى أو يُعاد بناؤه.

> **الاختبار العملي:** إن كنت تكتب عشرة ملفات لعرض قائمة بسيطة، فأنت تطبّق المعمارية على مشروع لا يحتاجها. الطبقات وسيلة لإدارة التعقيد، و**إضافتها لمشروع بسيط تصنع تعقيداً بدل أن تديره.**

والمعمارية ليست المكان المناسب لحسم سؤال الإطار. إن لم تختر بعد بين Flutter وReact Native، فابدأ من [مقارنة Flutter وReact Native](/ar/blog/flutter-vs-react-native)؛ مبادئ الطبقات هنا تنطبق على الاثنين.

## أخطاء التطبيق الشائعة

**1. طبقات بلا فائدة.** حالة استخدام تستدعي مستودعاً يستدعي API بلا أي منطق بينهما. إن كانت الطبقة مجرد تمرير، فاسأل عن جدواها؛ ودليل Flutter يوصي بإضافة حالات الاستخدام فقط حين تؤدي عملاً حقيقياً.

**2. تسريب تفاصيل البيانات إلى المجال.** كيان المجال يحوي حقولاً من استجابة الـAPI (مثل `created_at` بصيغة الخادم). **افصل نماذج البيانات عن كيانات المجال** وحوّل بينهما.

**3. المبالغة في التجريد.** واجهة مجرّدة لكل شيء «تحسّباً» لتغيير لن يحدث. جرّد ما تتوقع تغييره فعلاً.

**4. تجاهل إدارة الحالة.** المعمارية لا تحدد طريقة إدارة الحالة، فتحتاج قراراً منفصلاً (BLoC أو Riverpod أو نموذج العرض مع الأوامر كما في دليل Flutter) يعمل داخل طبقة العرض.

**5. نسخ بنية مشروع آخر.** المعمارية مبادئ لا وصفة جاهزة. فصّلها على مقاس مشروعك.

## بدائل أخف

إن كانت Clean Architecture مبالغة لمشروعك، فهناك مستويات وسط:

**الطبقتان اللتان يوصي بهما Flutter.** العروض ونماذج العرض في طبقة الواجهة، والمستودعات والخدمات في طبقة البيانات، بلا طبقة مجال. هذا هو الأساس في دليل Flutter نفسه، ويناسب معظم التطبيقات المتوسطة.

**نمط المستودع وحده.** ضع الوصول للبيانات خلف مستودع واترك الباقي مباشراً. يحل مشكلة تبديل مصدر البيانات بلا طبقات كاملة.

**ابدأ بسيطاً ثم طوّر.** ابدأ بطبقتين وأضف حالات الاستخدام حين يفرضها التعقيد فعلاً. **هذا أفضل من بناء طبقات مسبقاً لتعقيد قد لا يأتي.**

## الأسئلة الشائعة

### هل يحتاج كل تطبيق Flutter إلى طبقة مجال؟

لا. دليل المعمارية الرسمي من Flutter يصنّف طبقة المجال اختيارية، ويوصي بحالات الاستخدام فقط حين يدمج المنطق عدة مستودعات أو يكون معقداً جداً أو تتشاركه عدة نماذج عرض. التطبيق الصغير قليل المنطق يعمل جيداً بطبقة واجهة وطبقة بيانات فقط.

### أين يقع BLoC وRiverpod في Clean Architecture؟

داخل طبقة العرض. المعمارية تنظّم المسؤوليات في التطبيق كله، وBLoC وRiverpod يديران حالة الواجهة. **تستخدمهما معاً**؛ وتطبيق «تفوقي» مثلاً يجمع Clean Architecture مع BLoC.

### هل تؤخر Clean Architecture الإصدار الأول؟

نعم. ملفات أكثر وكود تحويل أكثر يعني أن الشاشات الأولى تأخذ وقتاً أطول. العائد يأتي لاحقاً في الصيانة والاختبار وإضافة الميزات. **في مشروع قصير العمر قد لا تصل إلى نقطة التعادل أصلاً**، ولهذا لا تناسب النماذج الأولية.

### هل يمكن نقل تطبيق Flutter قائم إلى Clean Architecture تدريجياً؟

نعم، وهذا غالباً الأفضل. ضع الوصول للبيانات خلف مستودعات أولاً، ثم استخرج حالات استخدام حيث يتكرر المنطق نفسه بوضوح بين نماذج العرض. الانتقال التدريجي أقل مخاطرة بكثير من إعادة هيكلة شاملة.

### كيف تسهّل طبقة المجال الاختبار؟

طبقة المجال لا تستورد Flutter ولا الشبكة، فيُغطّى منطقها باختبارات وحدة بلغة Dart فقط، وهي الأسرع والأرخص بحسب توثيق الاختبار في Flutter. راجع [دليل اختبار التطبيقات](/ar/blog/mobile-app-testing).

### هل تنطبق هذه المبادئ على React Native أيضاً؟

نعم. فصل المسؤوليات واتجاه الاعتماد للداخل مبادئ عامة لا تخص Flutter وحده، والذي يختلف هو الأدوات فقط.

## باختصار

- **استخدم Clean Architecture كاملة** للتطبيقات الكبيرة طويلة العمر ذات المنطق الحقيقي والفريق المتعدد.
- **استخدم طبقتَي Flutter الافتراضيتين** لمعظم التطبيقات المتوسطة، وأضف حالات الاستخدام حيث تؤدي عملاً حقيقياً فقط.
- **تجاوزها** في MVP والنماذج الأولية وتطبيقات العرض الصغيرة.
