# What is Flutter? A Complete Guide to Cross-Platform App Development

**Flutter is Google's free, open-source UI toolkit for building Android, iOS, web and desktop apps from a single [Dart](https://dart.dev/) codebase.** It draws every pixel of the interface itself, and since Flutter 3.27 it does so with the **Impeller** rendering engine on iOS and on Android API 29 and above. On our published rate card, a Flutter app costs **$5,000–$15,000** for a simple app up to **$45,000–$100,000** for an advanced platform, as of November 2026.

It is a strong default for a new cross-platform product — particularly an Arabic-first one — and the wrong choice in a handful of specific cases this guide lists. If you already know you want an app and need someone to scope it, see our [mobile app development services](/en/services/mobile-apps).

Official resources: the [Flutter website](https://flutter.dev/) and the [Flutter documentation](https://docs.flutter.dev/).

## What is Flutter?

Flutter is an open-source UI framework created by Google. You write the app once in Dart and build it for Android, iOS, Windows, macOS, Linux and the web.

Two design choices explain most of its behaviour, both described in the [Flutter architectural overview](https://docs.flutter.dev/resources/architectural-overview):

- **It has its own widgets.** Flutter "has its own implementations of each UI control, rather than deferring to those provided by the system". The app looks the same on every OS version, because it does not depend on the operating system's buttons and lists.
- **Release builds are compiled to machine code.** For release, Flutter apps are compiled directly to ARM or x64 machine code (or to JavaScript when targeting the web).

### Which rendering engine does Flutter use?

Older articles say Flutter renders with Skia. That is no longer true on mobile. According to the [Impeller documentation](https://docs.flutter.dev/perf/impeller) (Flutter 3.50 docs, updated August 2026):

| Platform | Renderer |
|---|---|
| iOS | Impeller — the only supported engine; switching to Skia is not possible |
| Android API 29+ | Impeller by default |
| Android below API 29, or without Vulkan | Falls back to the legacy OpenGL renderer automatically |
| macOS, Windows, Linux | Impeller by default since Flutter 3.47 |
| Web | Skia (a WebAssembly build); Impeller may come later |

Impeller ships inside the app, so performance improvements arrive with your next app release rather than waiting for the user's phone to get an OS update.

## Why has Flutter become so popular?

Before cross-platform frameworks matured, a company building for both stores maintained two apps:

- Kotlin and Java for Android
- Swift and Objective-C for iOS

That meant two teams, two codebases and every feature built twice. Cross-platform frameworks, Flutter and [React Native](/en/blog/react-native) among them, let one team share the interface and client logic across both.

Flutter's own [showcase](https://flutter.dev/showcase) lists Google products built with it — Google Pay, Google Classroom, Google Earth and NotebookLM among them — alongside companies such as BMW, eBay, Toyota and, closer to the Gulf, talabat and Expo City Dubai.

## How does Flutter work?

Everything on screen is a **widget**: text, images, buttons, lists, input fields, and the layout containers that arrange them. You compose small widgets into larger ones until you have a screen.

The official [Widget catalog](https://docs.flutter.dev/ui/widgets) lists the ready-made Material and Cupertino components.

When Flutter needs something the framework does not provide — a device sensor, a vendor SDK — it calls native code through a **platform channel**, or through `dart:ffi` for C-based APIs, which the architectural overview notes can be considerably faster because no serialisation is needed.

## Key advantages

- **Single codebase:** one project for Android, iOS, web and desktop.
- **Consistent rendering:** Flutter draws its own UI, so a design system looks identical on both platforms.
- **Hot reload:** code changes appear in the running app while keeping its current state.
- **Readable language:** Dart will feel familiar to anyone who knows Java, C# or TypeScript.
- **Package ecosystem:** [pub.dev](https://pub.dev/) hosts the community and official packages, including Firebase plugins.

## Flutter vs React Native, in short

Flutter draws its own widgets in Dart; React Native maps React components written in JavaScript or TypeScript to the platform's own native views. Team skills usually decide it: an existing React team points to React Native, a fresh team or an Arabic-first product leans Flutter. The full verdict, with a decision framework, is in [Flutter vs React Native: Which Should You Choose?](/en/blog/flutter-vs-react-native).

## Hot reload

The [hot reload documentation](https://docs.flutter.dev/tools/hot-reload) describes it as injecting updated source files into the running Dart runtime, after which the framework rebuilds the widget tree — "the current state of the app is preserved." It works only in debug mode, and changes to native Kotlin or Swift code still need a full restart.

In practice this is why Flutter interface work moves quickly: you adjust a layout and see it in place without navigating back to the screen.

## What Flutter actually costs to build in

Framework choice is rarely a line item on its own — it shows up as build time, team size, and what maintenance looks like a year later. Ranges from our published rate card, as of November 2026:

| Tier | Typical build time | USD | SAR / AED / QAR |
|---|---|---|---|
| Simple app | 6–10 weeks | $5,000 – $15,000 | SAR 18,800–56,300 · AED 18,400–55,100 · QAR 18,200–54,600 |
| Mid-complexity app | 3–5 months | $15,000 – $45,000 | SAR 56,300–168,800 · AED 55,100–165,300 · QAR 54,600–163,800 |
| Advanced app or platform | 5–9 months | $45,000 – $100,000 | SAR 168,800–375,000 · AED 165,300–367,300 · QAR 163,800–364,000 |

These are the same tiers used in [Mobile App Development Cost](/en/blog/mobile-app-development-cost). Flutter does not sit in a separate pricing bracket — the framework affects *how* the work is done far more than what it costs.

Three things move a quote more than the framework does:

1. **Backend scope.** A Flutter front end talking to an existing, documented API is a fraction of the work of one where the backend is built alongside it.
2. **Integration count.** Each payment gateway, government identity provider, or ERP connection carries its own build-and-certify cycle. See [Payment Gateways in the Gulf](/en/blog/gulf-payment-gateways).
3. **Design ownership.** Flutter draws its own pixels, which is a gift when you have a real design system and a liability when you do not — "make it look native" is unbounded work.

The single-codebase saving is real but smaller than "half the cost of two apps". Platform-specific work does not vanish: push notifications, deep links, in-app purchases, permissions, and store review all still need handling for each platform, even though the UI layer is shared.

For the regional cost picture independent of framework, see [App Development Cost in the Gulf](/en/blog/mobile-app-development-cost-gulf).

## When not to choose Flutter

Flutter is a strong default for cross-platform work, but there are cases where recommending it would be a mistake.

**Choose something else when:**

- **You already have a React team.** The productivity of a team writing a language it knows beats the theoretical merits of Dart. [React Native](/en/blog/react-native) is usually the right answer here.
- **The app is fundamentally one platform.** If iOS is nearly all of your users and always will be, native Swift gives you a better result with less indirection.
- **You depend on brand-new OS features.** Flutter reaches new platform APIs through plugins, which lag the OS release. If your product depends on a feature announced last month, you will be waiting or writing the platform channel yourself.
- **The app is mostly content.** A news or catalogue app with little interactivity may not justify an app at all — see [Mobile App or Responsive Website (PWA)?](/en/blog/app-vs-pwa).
- **Download size is critical.** The engine ships inside every Flutter app, so a minimal app is larger than a minimal native one. Flutter's [app-size guide](https://docs.flutter.dev/perf/app-size) warns that debug builds are not representative and shows how to measure real download size in Play Console and App Store Connect — do that before deciding.
- **Heavy platform-specific hardware work.** Deep camera pipelines, Bluetooth peripherals, or per-OS background processing end up written natively anyway, at which point the shared-codebase argument thins.

**A note on "Flutter is slow" claims:** most of them predate Impeller. The [Impeller docs](https://docs.flutter.dev/perf/impeller) state that it precompiles its shaders at engine-build time "so they don't compile at runtime" — runtime shader compilation being the usual explanation for the first-run animation stutter older Flutter apps were criticised for. Performance rarely decides the framework question today — team skills and integration requirements do.

## Hiring and team considerations

The framework you choose is a hiring decision you will live with for years.

**Pool size.** Dart is a smaller skill pool than JavaScript. In Stack Overflow's [2025 Developer Survey](https://survey.stackoverflow.co/2025/technology), 66% of respondents used JavaScript and 5.9% used Dart — a global figure, not a Gulf one, but the direction holds: staffing a large Flutter team quickly is harder than staffing a React one.

**What "a Flutter developer" should mean.** Widget composition is the easy part. The questions that separate real experience from tutorial familiarity:

- How do they handle state management, and *why* that choice?
- Have they shipped to both stores, including the review-rejection cycle?
- Can they write a platform channel when a plugin does not exist?
- Have they built RTL Arabic interfaces? General Flutter skill does not transfer automatically — the details are in [Arabic and RTL Support in Flutter](/en/blog/flutter-rtl-arabic-guide).

**The continuity risk.** A single Flutter developer who leaves mid-project is harder to replace than one of several React developers, simply because the pool is smaller. This is an argument for working with a team rather than an individual, weighed in [Freelancer or Development Agency?](/en/blog/freelancer-vs-agency).

## Is Flutter suitable for large projects?

Yes. The [showcase](https://flutter.dev/showcase) includes Google Pay, Google Ads, Nubank, BMW and Alibaba — finance, enterprise and commerce apps at scale.

As a project grows, how the code is organised matters more than the framework; [Clean Architecture in Flutter](/en/blog/clean-architecture-flutter) covers when that structure is worth its added complexity and when it is overkill.

For Arabic markets, RTL is what separates an acceptable app from a professional one. Flutter's localisation delegates set the default text direction from the locale, but mirrored icons, mixed-direction text and number formatting still need care — see [Arabic and RTL Support in Flutter](/en/blog/flutter-rtl-arabic-guide).

## Disadvantages

- **Larger minimum app size** than a bare native app, because the engine ships with it.
- **Plugin quality varies.** Some packages on pub.dev are well maintained; others are abandoned. Check the publisher and update history before depending on one.
- **New OS features arrive late** through plugins.
- **Dart is a new language** for most teams, though an easy one to pick up.

None of these rule Flutter out for a typical business app; they are what to check.

|---|---|---|

## A decision framework

Work through these in order. The first question that gives a clear answer usually settles it.

**1. Does your team already know something?**
An existing React team → React Native. An existing native team → keep going native. Only when there is no incumbent skill is the question genuinely open.

**2. Is this really a cross-platform product?**
If one platform carries the overwhelming majority of your users and revenue, cross-platform is solving a problem you do not have.

**3. How much of the app is not UI?**
Count the hardware access, background processing, and OS-specific integrations. If they dominate, the shared-codebase saving shrinks toward nothing.

**4. How important is a precise, consistent visual identity?**
Strict brand consistency across both platforms is where Flutter is strongest — it draws every pixel itself.

**5. Is Arabic RTL central to the product?**
Flutter sets direction for the whole widget tree from the locale. For Arabic-first products that is a practical advantage.

**6. What happens in year two?**
Who maintains it, and can you hire them? [In-House Maintenance or a Contract?](/en/blog/maintenance-inhouse-vs-contract) covers what that commitment involves.

> **The summary:** for a new cross-platform product with no existing team constraint, especially an Arabic-first one, Flutter is a strong default in 2026. The questions above are what turn that default into a decision.

## Frequently asked questions

### Is Flutter free to use commercially?

Yes. Flutter is open source and free, including for commercial apps. The cost of a Flutter app is engineering time, plus the usual store accounts.

### Does Flutter still use Skia?

Only on the web. On iOS, Impeller is the only supported renderer; on Android API 29 and above it is the default, with an automatic fallback to OpenGL on older or non-Vulkan devices; on desktop it has been the default since Flutter 3.47. Flutter web renders with a WebAssembly build of Skia.

### How much does it cost to build a Flutter app?

From our published rate card, as of November 2026: a simple app is $5,000–$15,000 (6–10 weeks), a mid-complexity app $15,000–$45,000 (3–5 months), and an advanced app or platform $45,000–$100,000 (5–9 months). Backend scope and the number of integrations move the number more than the framework does.

### Is a Flutter app half the price of two native apps?

No. The interface and client logic are shared, but push notifications, deep links, in-app purchases, permissions and store review still need platform-specific work on both sides. Expect a real saving, but not a halving.

### Is Flutter good for Arabic and RTL apps?

Yes. Once `flutter_localizations` is set up, the widgets localisation delegate sets the default text direction from the locale, and Material and Cupertino widgets adapt their layout. Icons that imply direction, mixed Arabic-English text and number formats still need deliberate handling.

### Can a Flutter app call native iOS and Android code?

Yes, through platform channels, or `dart:ffi` for C-based libraries. That is how a Flutter app reaches a sensor, payment SDK or OS feature that has no ready-made plugin.

### Will Google discontinue Flutter?

Google builds several of its own products with Flutter — Google Pay, Google Classroom and NotebookLM are on the official showcase — so an abrupt discontinuation is unlikely. The practical protection for any framework is a codebase where business logic is not entangled with the UI layer.
