# i18n for Arabic Products: Managing Translations at Scale

To run i18n well for an Arabic product: externalise every string from day one, namespace translation files by feature, use a library that implements the CLDR plural rules (Arabic has six plural forms, not two), write one string per sentence with named placeholders, and make CI fail when a key exists in one language but not the other. The framework takes a day to set up; the workflow is what keeps Arabic accurate a year later.

Internationalisation starts easy — one JSON file and a `t()` function. Then the product grows, three developers add strings in different styles, marketing rewrites the onboarding, and nobody knows which Arabic strings are stale. This guide covers structure and workflow. For the wider scope of Arabic support, see the [complete Arabic localisation guide](/en/blog/arabic-localization-guide); an i18n layer from the first commit is standard in our [web](/en/services/web-development) and [mobile](/en/services/mobile-apps) builds.

---

## Build the layer even if you launch in one language

The cheapest localisation decision available: set up i18n in phase one, even when Arabic ships later.

**What it costs now:** a few days. Install a library, externalise strings as you write them, use [logical CSS properties](/en/blog/rtl-css-guide).

**What it costs later:** weeks. Every hard-coded string has to be found — and they hide in validation messages, email templates, error handlers, chart labels and PDF generators.

**The asymmetry is large enough** that building the layer is worth it even if Arabic never ships.

## Structuring translation files

**Namespace by feature, not by type.** The instinct is `buttons.json`, `labels.json`, `errors.json`. That scales badly, because working on checkout means touching every file.

```
locales/
  en/
    common.json
    auth.json
    checkout.json
  ar/
    common.json
    auth.json
    checkout.json
```

**Key names should describe meaning, not content.** `auth.login.submitButton` survives a copy change; `auth.login.signInNow` becomes a lie the moment marketing rewrites it to "Get started".

**Never use the English string as the key.** It seems convenient, and it makes every copy edit a key rename across the codebase and every translation file.

**Keep the same key set in both languages.** A key present in English and absent in Arabic should fail a check, not silently fall back in production.

## Plurals: Arabic has six forms

This is where naive i18n breaks, and it breaks silently.

English has two plural categories. Arabic has six. The [CLDR plural rules](https://www.unicode.org/cldr/charts/latest/supplemental/language_plural_rules.html) define them:

| Category | Numbers | Example |
|---|---|---|
| `zero` | 0 | لا توجد عناصر |
| `one` | 1 | عنصر واحد |
| `two` | 2 | عنصران |
| `few` | 3–10, 103–110 … | 3 عناصر |
| `many` | 11–99, 111–199 … | 11 عنصراً |
| `other` | 100–102, 200–202 … | 100 عنصر |

**In ICU MessageFormat** (FormatJS, next-intl, Flutter ARB files):

```
{count, plural,
  zero {لا توجد عناصر}
  one {عنصر واحد}
  two {عنصران}
  few {# عناصر}
  many {# عنصراً}
  other {# عنصر}
}
```

**In i18next,** the [plurals guide](https://www.i18next.com/translation-function/plurals) uses suffixed keys based on `Intl.PluralRules`:

```json
{
  "items_zero": "لا توجد عناصر",
  "items_one": "عنصر واحد",
  "items_two": "عنصران",
  "items_few": "{{count}} عناصر",
  "items_many": "{{count}} عنصراً",
  "items_other": "{{count}} عنصر"
}
```

**Verify CLDR support before committing to a library.** `Intl.PluralRules` returns all six Arabic categories ([MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/PluralRules) shows `ar-EG` selecting `zero`, `one`, `two`, `few` and `many`), and libraries built on it inherit that. A hand-rolled `count === 1 ? a : b` produces wrong Arabic for most quantities, in a way English-speaking reviewers cannot see.

**React Native caveat:** the i18next documentation notes that Hermes does not implement `Intl.PluralRules`, so add a polyfill or only the English-style forms will resolve.

**The dual matters.** Arabic has a specific form for exactly two, and getting it wrong reads as carelessness to native readers.

## Interpolation and word order

**Never concatenate translated fragments.** Word order differs between languages, so assembled sentences come out wrong.

```js
// Wrong — assumes English word order
t("youHave") + " " + count + " " + t("newMessages")

// Right — one string, one meaning
t("newMessages", { count })
```

**Name your variables.** `{{name}}` and `{{count}}` tell a translator what they are working with; `{{0}}` and `{{1}}` do not.

**Watch bidirectional interpolation.** A Latin-script value — an order code, an email address, a product name — inside an Arabic sentence needs isolation, or punctuation lands on the wrong side. Wrap it in `<bdi>` in HTML or in the U+2066 … U+2069 isolate characters in plain text; [Arabic numerals and formats](/en/blog/arabic-numerals-formats) has the details.

**Give context for ambiguous keys.** "Post" is a verb and a noun. Most formats support a description field — Flutter's ARB files use `@key` metadata with a `description` — and translators need it.

## Workflow: the part that actually breaks

The technical setup is a day. The workflow decides whether Arabic is still accurate in a year.

| Approach | Suits | Weakness |
|---|---|---|
| Files in the repository | Small teams, developer-authored copy | Non-developers cannot contribute easily |
| Translation management platform | Growing products, external translators | Cost, sync complexity |
| Spreadsheet with import script | Small budgets, occasional updates | Manual and error-prone at scale |

**Files in the repository work well at first**; a translation platform becomes worthwhile once non-developers need to edit copy regularly.

**Whatever you choose, three rules hold:**

**Fail the build on missing keys.** A key present in English and missing in Arabic should break CI, not fall back silently in production.

**Detect unused keys.** Files accumulate strings for deleted features. A periodic scan for keys absent from the codebase keeps this in check.

**Never machine-translate into production without review.** Machine translation can be a first draft for volume content. Shipped unreviewed, it reads as machine-produced to fluent readers and costs more credibility than it saved in time.

## Framework notes

**React / Next.js.** `react-i18next` and `next-intl` both handle Arabic plurals through CLDR rules. Put each language on its own URL (for example `/ar/...` and `/en/...` via a `[lang]` route segment): Google [recommends separate URLs per language with hreflang annotations](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites) rather than switching language by cookie.

**Flutter.** `flutter gen-l10n` generates a typed getter per key from the template ARB file, so referencing a key that does not exist is a compile error. Translations missing from `app_ar.arb` are a different case: the [Flutter docs](https://docs.flutter.dev/ui/accessibility-and-internationalization/internationalization) describe the `untranslated-messages-file` option, which writes them to a JSON file — fail CI when that file is not empty. For a shipped example of an Arabic-first Flutter app, see [Tafawwoq](/en/portfolio/tafawwoq-educational-app), our educational app with a full Arabic RTL interface.

**Backend.** Emails, SMS, PDF invoices and API error messages all need translation, and they are the most commonly overlooked surface. An Arabic app that sends English transactional emails is an avoidable inconsistency.

## Frequently asked questions

### Which numbers use which Arabic plural form?

Per the CLDR rules: `zero` for 0, `one` for 1, `two` for 2, `few` when the last two digits are 3–10 (3–10, 103–110), `many` when they are 11–99 (11–99, 111–199), and `other` for the rest, such as 100–102. `Intl.PluralRules("ar")` returns these categories for you.

### Do i18next and FormatJS handle Arabic plurals?

Yes. i18next selects suffixed keys (`_zero`, `_one`, `_two`, `_few`, `_many`, `_other`) using `Intl.PluralRules`, and FormatJS and next-intl use ICU MessageFormat plural syntax. In React Native, i18next's docs note that Hermes lacks `Intl.PluralRules`, so add a polyfill.

### Should I set up i18n if I am only launching in English?

Yes, if Arabic is anywhere on your roadmap. Building the layer costs a few days now; retrofitting costs weeks, because hard-coded strings hide in validation messages, email templates, error handlers and PDF generators.

### Should I use the English text as my translation key?

No. It turns every copy edit into a key rename across the codebase and every translation file. Use keys that describe meaning, such as `auth.login.submitButton`.

### Does Flutter's gen-l10n catch missing Arabic translations?

Partly. A key missing from the template ARB is a compile error, because the getter does not exist. A key present in `app_en.arb` but missing from `app_ar.arb` is reported as untranslated — on the command line, or in a JSON file if you set `untranslated-messages-file`. Make CI fail when that file lists anything.

### Why should I not concatenate translated strings?

Because word order differs between languages, a sentence assembled from fragments in English order comes out wrong in Arabic. Use one string per sentence with named placeholders, and give translators context notes for ambiguous keys.

### What is the most commonly overlooked i18n surface?

The backend: emails, SMS, PDF invoices and API error strings are routinely left in English while the interface is fully translated. Include them in scope from the start.

## Getting it right from the first commit

Externalise strings, pick a CLDR-aware library, write all six Arabic plural forms, keep sentences whole, and let CI police missing and untranslated keys. That is what keeps Arabic accurate after the first release, which is where most products quietly degrade.
