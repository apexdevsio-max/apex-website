# Arabic and RTL Support in React Native: A Practical Guide

React Native supports Arabic right-to-left layout through `I18nManager`, plus logical style properties such as `marginStart` and `paddingEnd` that resolve against the current direction. Two things catch teams out: direction changes made through `I18nManager` only take effect on the next app start, and third-party libraries are where RTL actually breaks. Decide how your app will switch direction before you style the first screen, and test RTL from week one.

The gap between "we called `I18nManager.forceRTL(true)`" and "this feels like an Arabic app" is where most projects lose time. This guide covers the React Native specifics, with each API checked against the React Native documentation. For the full scope of what localisation involves beyond direction, see the [complete Arabic localisation guide](/en/blog/arabic-localization-guide); for help building the app itself, see our [mobile app development services](/en/services/mobile-apps).

## `I18nManager` and the restart problem

RTL in React Native runs through `I18nManager`:

```js
import { I18nManager } from "react-native";

I18nManager.isRTL;           // true when the app is currently laid out RTL
I18nManager.allowRTL(true);  // allow RTL when the device language is RTL
I18nManager.forceRTL(true);  // force RTL regardless of device language
```

**The catch:** the [React Native docs](https://reactnative.dev/docs/i18nmanager) state that `allowRTL` and `forceRTL` changes "take effect on the next application start, not immediately", and that both settings persist across restarts. They also describe `forceRTL` as "primarily useful for testing RTL layouts during development", warning that forcing RTL in production "requires a full app restart to take effect, which makes for a poor user-experience".

That produces an awkward experience: an in-app language switcher that appears to do nothing until the app is relaunched. Your options:

**Option 1 — follow the device language.** Allow RTL, read `I18nManager.isRTL`, and let users who want Arabic set their phone to Arabic. The simplest and most predictable approach, and what the docs steer production apps towards.

**Option 2 — in-app switch with a restart.** Call `allowRTL`/`forceRTL`, then reload the app (for example with a restart library such as `react-native-restart`) and tell the user what is about to happen. Crude, but it always works.

**Option 3 — manage direction in React.** The [layout props](https://reactnative.dev/docs/layout-props) include `direction` (`'inherit' | 'ltr' | 'rtl'`). Setting it on your root view from your own language state flips every `marginStart` and `flexDirection: "row"` beneath it with no restart. Native pieces outside your view tree — some navigation transitions, gestures, system dialogs — may still follow `I18nManager`, so test them.

> **Choose this early.** It shapes how every component is written. Retrofitting option 3 onto an app built around `I18nManager` means touching every screen.

## Styles: what mirrors and what does not

The properties to know, as the layout docs define them:

| Physical (avoid) | Logical (use) |
|---|---|
| `marginLeft` | `marginStart` |
| `marginRight` | `marginEnd` |
| `paddingLeft` | `paddingStart` |
| `paddingRight` | `paddingEnd` |
| `left` / `right` | `start` / `end` |
| `borderLeftWidth` | `borderStartWidth` |

The docs spell it out: when direction is `rtl`, `marginStart` is equivalent to `marginRight`, and `start` is equivalent to `right` (and takes precedence over `left` and `right`). **Write logical properties everywhere and the layout mirrors for free.** Write physical ones and you will maintain a parallel set of RTL overrides that drift out of sync.

**`flexDirection: "row"` follows the layout direction**, so rows mirror under RTL. When a row must keep a fixed order — media controls, a numeric keypad — set `direction: "ltr"` on that container rather than reaching for `row-reverse`, which reverses in both directions.

**Don't hard-code `textAlign: "right"` for Arabic.** It breaks the moment the same component renders in English. The default `textAlign` is `"auto"`; leave it, check the result on both platforms, and if a component needs explicit alignment, derive it from your direction state (`I18nManager.isRTL` or your own flag).

## What must never mirror

Automatic mirroring is a blunt instrument. These keep their orientation:

- **Media playback controls** — play points right, in every language
- **Clocks and timers**
- **Charts with a time axis**
- **Phone numbers, IBANs, card numbers, version numbers**
- **Most logos and brand marks**
- **Code blocks and terminal output**

For icons, flip only the directional ones yourself:

```js
const flipForRTL = I18nManager.isRTL ? { transform: [{ scaleX: -1 }] } : null;

<Image source={backArrow} style={[styles.icon, flipForRTL]} />
```

Apply this only to back arrows, next/previous chevrons and send icons. Applying it to a play button or a clock produces exactly the bug this section exists to prevent. Check your icon library first: some icon sets ship separate "forward" and "back" glyphs you can swap instead of flipping.

## Fonts and typography

The system Arabic font differs between iOS and Android, visibly enough that designers notice. Bundling a font gives you consistency:

```js
// After adding the font files to the project
const styles = StyleSheet.create({
  arabic: {
    fontFamily: "Cairo",
    fontSize: 16,
    lineHeight: 28,     // lineHeight is in points: about 1.75 × fontSize
    letterSpacing: 0,   // never anything else for Arabic
  },
});
```

**Three rules that matter more than font choice:**

**`letterSpacing` must be 0.** Arabic letters join, and spacing breaks the joins — MDN's CSS reference warns it "may lead to the text looking broken", and the same applies on mobile. It is the single most common Arabic typography bug.

**`lineHeight` needs more room than English.** In React Native it is an absolute value, not a multiplier, so compute it from the font size: around 1.7–1.8 × the font size is a reasonable start for Arabic body text. [Arabic web fonts](/en/blog/arabic-web-fonts) explains why Arabic needs the extra space and covers subsetting, which applies to bundled app fonts too.

**Test on both platforms with real text.** Android and iOS render Arabic differently enough that a layout verified on one can break on the other, particularly around line breaking and font fallback.

## Third-party libraries — where RTL actually breaks

This is the real cost centre, and it is rarely in the estimate.

**Libraries that commonly need attention:** navigation transitions and drawers, carousels and sliders, swipe-to-action lists, date pickers, charts, and anything with a built-in back button.

**How they break:** gestures move the wrong way, drawers open from the wrong side, carousel indexes run backwards, or the library hard-codes `marginLeft` internally where you cannot reach it.

**How to handle it:**
1. **Test RTL early.** Enable it in week one with placeholder text, not in month four. A carousel that scrolls backwards is a small fix on day five and an architectural argument on day ninety.
2. **Check RTL support before adopting a library.** Search its issues for "RTL" — the presence and age of open RTL issues tells you what you need to know.
3. **Wrap third-party components** in your own, so a fix lives in one place.
4. **Plan time for workarounds** rather than assuming every library behaves.

## Bidirectional text

Arabic sentences containing English product names, numbers or codes need care, or punctuation lands in visually wrong places — a `#` on the wrong side of an order code, or phone-number digit groups in reverse order.

**`writingDirection` is not a cross-platform fix.** The [text style docs](https://reactnative.dev/docs/text-style-props) list it as iOS-only (`'auto' | 'ltr' | 'rtl'`).

**What works on both platforms** is putting the direction into the string itself with Unicode isolates — left-to-right isolate U+2066 and pop directional isolate U+2069, which the [W3C recommends](https://www.w3.org/International/questions/qa-bidi-unicode-controls) for plain text where markup is unavailable:

```js
const ltr = (s) => `\u2066${s}\u2069`;

<Text>{`رقم الطلب: ${ltr("#A-1042")}`}</Text>
<Text>{`للتواصل: ${ltr("+966 50 123 4567")}`}</Text>
```

Test this on the oldest Android version you support. **Where it shows up:** prices with currency codes, version numbers in Arabic sentences, addresses and user-generated content. If your product displays user content, test with deliberately mixed Arabic and English input.

## How React Native compares to Flutter here

Both can produce good Arabic apps. The difference is how much manual work stands between you and that outcome.

**Flutter** builds direction into the widget tree: `Directionality` is a first-class widget, `EdgeInsetsDirectional` is the normal way to write padding, and Material icons such as `Icons.arrow_back` mirror themselves through `matchTextDirection`. Our own shipped Arabic app, [Tafawwoq](/en/portfolio/tafawwoq-educational-app), is built in Flutter with a full Arabic RTL interface.

**React Native** surfaces RTL through `I18nManager`. It works, but restarts on direction changes are awkward, icons need manual flipping, and the third-party ecosystem is less consistent about RTL.

**In practice:** for an Arabic-first product with no existing team constraint, Flutter needs less RTL work. For a team that already writes React, that advantage rarely outweighs their existing skills — React Native is still a sound choice; plan more time for RTL testing. [Flutter vs React Native](/en/blog/flutter-vs-react-native) covers the wider decision, and [Arabic and RTL support in Flutter](/en/blog/flutter-rtl-arabic-guide) is the equivalent guide.

## Pre-launch checklist

- [ ] Direction strategy chosen: follow the device, in-app switch with restart, or root `direction` style
- [ ] Every style uses `start`/`end` rather than `left`/`right`
- [ ] No hard-coded `textAlign: "right"` for Arabic
- [ ] Directional icons flipped; play buttons, clocks and charts left alone
- [ ] Bundled Arabic font with `letterSpacing: 0` and a `lineHeight` around 1.7–1.8 × the font size
- [ ] Every third-party component verified under RTL
- [ ] Navigation transitions and drawers open from the correct side
- [ ] Phone numbers, codes and IBANs isolated with U+2066 … U+2069
- [ ] Tested on both iOS and Android with real Arabic content
- [ ] Reviewed by a native Arabic reader on a real device

## Frequently asked questions

### Why doesn't `I18nManager.forceRTL` change the layout straight away?

Because, per the React Native docs, `allowRTL` and `forceRTL` changes take effect on the next application start, and the setting persists across restarts. Reload the app after calling it, follow the device language instead, or set the `direction` style on your root view from your own language state.

### Should I use `forceRTL` in a production app?

The React Native docs advise against it: they describe `forceRTL` as primarily for testing RTL during development and warn that forcing RTL in production requires a full restart, which is a poor user experience. In production, follow the device language and read `I18nManager.isRTL`, or manage direction yourself.

### Should I use `marginLeft` or `marginStart` in React Native?

`marginStart` and `marginEnd`. The layout docs define `marginStart` as `marginLeft` in LTR and `marginRight` in RTL, so the layout mirrors with no extra code. Physical properties force you to maintain RTL overrides.

### Why do phone numbers display back to front in my Arabic screens?

Inside RTL text, the spaces between digit groups take the surrounding direction. `writingDirection` would help only on iOS, so isolate the number in the string with `\u2066` before and `\u2069` after, which works on both platforms.

### Why does my Arabic text look broken in React Native?

Almost always `letterSpacing`. Any non-zero value separates letters that should join. Set `letterSpacing: 0` for Arabic. The next most common cause is a `lineHeight` copied from English; Arabic needs roughly 1.7–1.8 × the font size.

### How do I flip icons for RTL in React Native?

Apply `transform: [{ scaleX: -1 }]` when `I18nManager.isRTL` is true, and only to directional icons such as back arrows and send buttons. Never to play buttons, clocks or time-axis charts.

### Is Flutter better than React Native for Arabic apps?

Flutter needs less manual RTL work because direction is part of the widget tree and Material's directional icons mirror automatically. If your team already writes React, that rarely outweighs their existing skills — use React Native and plan more RTL testing time.
