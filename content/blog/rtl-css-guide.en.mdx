# RTL in CSS: Building Bidirectional Layouts Properly

Build right-to-left layouts with one stylesheet: put `dir="rtl"` and `lang="ar"` on the `<html>` element, and write every spacing and position rule with logical properties — `margin-inline-start` instead of `margin-left`, `inset-inline-end` instead of `right`, `text-align: start` instead of `left`. The layout then mirrors itself, and there is no RTL stylesheet to keep in sync.

The old approach was a second stylesheet — `styles-rtl.css`, loaded for Arabic, overriding every `margin-left` with a `margin-right`. It worked, and it drifted out of sync, because every new component needed two implementations and only one of them got tested. This guide covers the modern approach in detail. For the wider scope of Arabic support, see the [complete Arabic localisation guide](/en/blog/arabic-localization-guide); bilingual front ends built this way are the default in our [web development services](/en/services/web-development).

## Set direction once, correctly

Direction belongs on the `<html>` element, alongside the language:

```html
<html lang="ar" dir="rtl">
```

**Both attributes matter.** `dir` sets the base direction for layout and the bidirectional algorithm; `lang` drives font selection, hyphenation and screen-reader pronunciation. The [W3C's guidance](https://www.w3.org/International/questions/qa-html-dir) is explicit that `lang` does not set direction — you always need `dir` as well.

**Don't set base direction with CSS.** The same W3C article says: "Do not use CSS to apply base direction in HTML pages." Direction can change the meaning of content, so it belongs in markup. CSS `direction` exists, but the attribute is the source of truth.

## Logical properties: the whole trick

Physical properties refer to fixed sides. Logical properties refer to the *start* and *end* of the text flow, which swap automatically under RTL.

| Physical | Logical |
|---|---|
| `margin-left` | `margin-inline-start` |
| `margin-right` | `margin-inline-end` |
| `padding-left` | `padding-inline-start` |
| `padding-right` | `padding-inline-end` |
| `border-left` | `border-inline-start` |
| `left` / `right` | `inset-inline-start` / `inset-inline-end` |
| `text-align: left` | `text-align: start` |
| `border-top-left-radius` | `border-start-start-radius` |
| `width` / `height` | `inline-size` / `block-size` |

**The shorthands are convenient:**

```css
.card {
  margin-inline: 1rem 2rem;   /* start, end */
  padding-block: 1rem;        /* top and bottom */
  border-start-start-radius: 8px;
}
```

**Browser support is no longer the obstacle.** MDN marks [`margin-inline-start`](https://developer.mozilla.org/en-US/docs/Web/CSS/margin-inline-start) as Baseline widely available, working across browsers since January 2020. Check MDN's compatibility table for the newer shorthands if you support older devices.

**The migration strategy that works:** add a lint rule that rejects physical properties in new code (Stylelint has plugins for this), and convert existing components as you touch them. A big-bang rewrite is rarely justified; the drift stops the moment new code stops adding to it.

## Flexbox and grid mirror for free

This is the part people do not expect: **flex and grid layouts follow the inline direction**, so they mirror under RTL without any extra code.

```css
.toolbar {
  display: flex;
  gap: 1rem;
  justify-content: flex-start;  /* the right-hand edge in an RTL page */
}
```

`flex-start`, `flex-end`, `justify-content` and grid's `start`/`end` lines all follow the text direction.

**When a row must not mirror** — a media player's controls, for instance — give that container its own direction in markup:

```html
<div class="player-controls" dir="ltr">…</div>
```

**Avoid `row-reverse` as an RTL fix.** It reverses in *both* directions, so a layout that relies on it will be wrong in one of them.

## What must never mirror

Automatic mirroring is a blunt tool. These keep their orientation in every language:

- **Media controls** — play points right
- **Clocks and timers**
- **Charts with a time axis**
- **Phone numbers, IBANs, card numbers, version numbers**
- **Code blocks and terminal output**
- **Most logos**

**For code blocks,** mark them left-to-right in markup where you control it:

```html
<pre dir="ltr"><code>const total = items.reduce(sum, 0);</code></pre>
```

Where code blocks come out of a Markdown renderer you cannot annotate, a stylesheet rule is the practical fallback:

```css
pre {
  direction: ltr;
  text-align: left;
  unicode-bidi: isolate;
}
```

Without one of these, code inside an Arabic article renders with operators and punctuation at the wrong ends of lines.

**For icons,** flip only the directional ones:

```css
[dir="rtl"] .icon-arrow-back,
[dir="rtl"] .icon-chevron-next {
  transform: scaleX(-1);
}
```

Never apply this globally. A mirrored play button or clock is exactly the bug this section prevents.

## Typography rules that differ

Three CSS rules matter more for Arabic than font choice does.

**`letter-spacing` must be zero.** MDN's [`letter-spacing` page](https://developer.mozilla.org/en-US/docs/Web/CSS/letter-spacing) warns that Arabic-script text expects connected letters to stay connected and that letter spacing "may lead to the text looking broken". Reset it for Arabic, because it usually arrives from a heading style built for Latin type.

```css
:lang(ar) {
  letter-spacing: 0;
  line-height: 1.8;
}
```

**Line height needs more room.** The 1.4–1.5 that reads comfortably in English feels cramped in Arabic; 1.7–1.8 is a better baseline for body text. [Arabic web fonts](/en/blog/arabic-web-fonts) explains why and covers loading and subsetting.

**`text-transform` does nothing useful.** Arabic has no letter case, so `uppercase` does nothing to Arabic text — but it still changes any embedded Latin text, often unintentionally.

## Bidirectional text and embedded content

Arabic sentences containing English product names, numbers or URLs need isolation, or punctuation lands in visually wrong positions.

**Use `<bdi>` for any embedded text whose direction you cannot predict:**

```html
<p>اشترِ <bdi>iPhone 15 Pro</bdi> الآن.</p>
```

[MDN describes `<bdi>`](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/bdi) as telling the browser's bidirectional algorithm to treat its contents in isolation, and notes it behaves as if `dir="auto"` were set. That is what you want for user names, product titles and search results. MDN also advises against reproducing it with `unicode-bidi: isolate` on a `<span>`, because the CSS approach is not semantic.

**When you know the direction, say so:**

```html
<span dir="ltr">+966 50 123 4567</span>
```

[Arabic numerals and formats](/en/blog/arabic-numerals-formats) covers this in depth, including the `Intl` APIs that format currency correctly.

## Testing

**Test early, not before launch.** Switching a mature codebase to RTL for the first time surfaces dozens of small breakages at once. Enable it in week one.

**A quick check without changing your app:** set `dir="rtl"` on `<html>` in devtools and click through. Most layout bugs are visible immediately.

**Automate the regression check.** Visual regression snapshots in both directions catch the component a refactor quietly broke in one of them.

**What to look for specifically:**
- Shadows and gradients with a directional offset
- Absolutely positioned elements using `left`/`right`
- Background image positions
- Transform origins
- Scroll position in horizontally scrolling containers
- `::before`/`::after` content positioned physically

## Frequently asked questions

### Do I need a separate RTL stylesheet?

No. Logical properties like `margin-inline-start` resolve correctly in both directions from a single stylesheet. A separate RTL file drifts out of sync as components are added, because usually only one version gets tested.

### Can I rely on CSS logical properties in production?

Yes for the core properties. MDN marks `margin-inline-start` as Baseline widely available, working across browsers since January 2020. Check the compatibility tables of any newer shorthand you use against the oldest browsers you support.

### Does flexbox mirror automatically in RTL?

Yes. Flex and grid follow the inline direction, so `flex-start`, `justify-content` and grid lines follow `dir` automatically. Don't use `row-reverse` as an RTL solution — it reverses in both directions, so it will be wrong in one of them.

### Should I set direction with the `dir` attribute or CSS `direction`?

With the `dir` attribute. The W3C advises against using CSS to apply base direction in HTML, because direction is part of the content's meaning. Use `dir="rtl"` on `<html>` and `dir` on specific elements; keep CSS `direction` for fallbacks such as rendered code blocks you cannot annotate.

### Why does my Arabic heading look broken?

Almost certainly `letter-spacing`, often inherited from a design-system heading style. Arabic letters join, and any non-zero spacing separates them. Set `letter-spacing: 0` for Arabic text, for example with a `:lang(ar)` rule.

### How do I stop code blocks breaking in an RTL page?

Mark them left-to-right: `<pre dir="ltr">` where you control the markup, or a `pre { direction: ltr; text-align: left; unicode-bidi: isolate; }` rule for Markdown-rendered content. Without this, operators and punctuation end up at the wrong ends of lines.

### How do I test RTL without switching my whole app?

Set `dir="rtl"` on the `<html>` element in browser devtools and click through. Most layout bugs show immediately. For ongoing protection, add visual regression snapshots in both directions.

## Summing up

`dir` and `lang` on `<html>`, logical properties everywhere, flex and grid left to follow the direction, and a short, explicit list of things that keep their orientation. Add `letter-spacing: 0`, more line height and `<bdi>` for embedded text, and one stylesheet serves both languages.
