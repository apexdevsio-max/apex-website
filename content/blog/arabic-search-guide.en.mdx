# Arabic Search: Why It Fails and How to Fix It

Arabic search fails because the same word can be written several ways — `أحمد` or `احمد`, `مدرسة` or `مدرسه`, with or without diacritics — and an engine configured for English compares them as different strings. The fix is to normalise both the indexed text and every query: unify alef variants to `ا`, taa marbuta to `ه`, alef maqsura to `ي`, strip diacritics and tatweel, and then apply a light Arabic stemmer so `الكتاب` matches `كتاب`. Search engines such as Elasticsearch do this out of the box once you select their Arabic analyser.

A typical report: a user searches your Arabic catalogue for a product that is definitely there and gets nothing. The team suspects the query layer. It is usually the text. This guide covers what to normalise and how; search like this is part of the Arabic builds in our [web development services](/en/services/web-development). For the wider scope, see the [complete Arabic localisation guide](/en/blog/arabic-localization-guide).

## Why exact matching fails

Four characteristics of written Arabic break naive search.

**1. Alef variants.** Alef has several forms — `ا`, `أ`, `إ`, `آ` — and writers use them inconsistently. A search for `احمد` will not match `أحمد` unless you normalise. This is one of the most common causes of missing results.

**2. Taa marbuta and haa.** The word-final `ة` is frequently typed as `ه`. `مدرسة` and `مدرسه` are the same word to a reader and different strings to a database.

**3. Diacritics (tashkeel).** Marks such as fatha and damma are optional. Content entered with them will not match a query typed without them, and users almost never type them.

**4. Alef maqsura and yaa.** Word-final `ى` and `ي` are used interchangeably by many writers — `على` and `علي`.

**Digits add a fifth case.** A query typed with Eastern Arabic digits (`١٥`) will not match `15` in your catalogue, and Persian or Urdu keyboards produce yet another digit set (`۱۵`).

**The consequence:** one Arabic word can have four or more written forms that all look correct to a reader. Exact matching finds one of them.

## Normalisation: the core fix

Normalisation means converting text to a canonical form before comparing. Apply it to both the indexed content and the incoming query — normalising only one side achieves nothing.

**A working set of transformations in JavaScript:**

```js
function normalizeArabic(text) {
  return text
    .normalize("NFC")
    // Diacritics (harakat, U+064B–U+065F) and the superscript alef (U+0670)
    .replace(/[\u064B-\u065F\u0670]/g, "")
    // Tatweel (kashida)
    .replace(/\u0640/g, "")
    // Alef with hamza or madda → bare alef
    .replace(/[\u0622\u0623\u0625\u0671]/g, "\u0627")
    // Taa marbuta → haa
    .replace(/\u0629/g, "\u0647")
    // Alef maqsura → yaa
    .replace(/\u0649/g, "\u064A")
    // Hamza on waw and yaa (optional; Lucene's normaliser leaves these alone)
    .replace(/\u0624/g, "\u0648")
    .replace(/\u0626/g, "\u064A")
    // Eastern Arabic and Persian digits → Western digits
    .replace(/[\u0660-\u0669]/g, (d) => String(d.charCodeAt(0) - 0x0660))
    .replace(/[\u06F0-\u06F9]/g, (d) => String(d.charCodeAt(0) - 0x06F0))
    .toLowerCase()
    .trim();
}

normalizeArabic("أَحْمَد");     // "احمد"
normalizeArabic("آيفون ١٥");   // "ايفون 15"
```

**Write the ranges as code points, not pasted characters.** A diacritics range typed as two pasted marks is easy to get wrong: a range that runs up to U+0670 also swallows the Eastern Arabic digits U+0660–U+0669, silently deleting every number in the text.

**Store the normalised form alongside the original.** Display the original — normalised text looks subtly wrong — and search against the normalised column.

**Don't normalise your source of truth.** Names, legal text and religious content may need their exact forms preserved. Normalisation is for the search index only.

## Let your search engine do it

Hand-rolled normalisation works for simple cases, but mature search engines ship Arabic analysis, including stemming, which regular expressions cannot do well.

**Elasticsearch / OpenSearch.** The built-in `arabic` analyser is the simplest start. Its [documented equivalent](https://www.elastic.co/guide/en/elasticsearch/reference/current/analysis-lang-analyzer.html) shows the chain, which you can rebuild to customise:

```json
{
  "settings": {
    "analysis": {
      "filter": {
        "arabic_stop": { "type": "stop", "stopwords": "_arabic_" },
        "arabic_stemmer": { "type": "stemmer", "language": "arabic" }
      },
      "analyzer": {
        "rebuilt_arabic": {
          "tokenizer": "standard",
          "filter": [
            "lowercase",
            "decimal_digit",
            "arabic_stop",
            "arabic_normalization",
            "arabic_stemmer"
          ]
        }
      }
    }
  }
}
```

- `decimal_digit` converts other digit sets, including Eastern Arabic, to `0–9`.
- `arabic_normalization` applies Lucene's [ArabicNormalizer](https://lucene.apache.org/core/9_0_0/analysis/common/org/apache/lucene/analysis/ar/ArabicNormalizer.html): hamza-seated alef to bare alef, teh marbuta to heh, alef maksura to yeh, and removal of harakat and tatweel.
- The Arabic stemmer applies Lucene's [ArabicStemmer](https://lucene.apache.org/core/9_0_0/analysis/common/org/apache/lucene/analysis/ar/ArabicStemmer.html), which removes the attached definite article, conjunctions and prepositions and strips common suffixes. That is **light stemming, not root extraction**: `الكتاب` and `وبالكتاب` match `كتاب`, but the broken plural `كتب` does not.

**PostgreSQL.** PostgreSQL's source includes a Snowball Arabic stemmer, so full-text search with an Arabic configuration is available and far better than `LIKE '%term%'` in both relevance and speed. Diacritics need care: the documentation describes the default [`unaccent`](https://www.postgresql.org/docs/current/unaccent.html) rules as aimed at European accents, so supply a custom rules file that deletes the harakat, or normalise in application code before indexing.

**Managed search services** (Algolia, Typesense, Meilisearch and others) can save you running a cluster. Check each one's Arabic documentation for normalisation and stemming support, and run the test set below against it before committing.

## Stemming and the definite article

Arabic is morphologically rich — prefixes and suffixes attach directly to words, which defeats substring matching.

**The definite article `ال` is the most common case.** `الكتاب` (the book) and `كتاب` (book) should match. A stemmer handles this; naive matching does not.

**Prefixes stack:** `وبالكتاب` contains the conjunction `و`, the preposition `ب`, the article `ال` and the noun. A reader parses this instantly; a substring search does not.

**Use an analyser rather than writing prefix-stripping rules.** Hand-written rules over-strip — removing `ال` from a word that genuinely begins with those letters produces wrong matches, and the failure is silent.

**Know the limit of light stemming.** Plurals that change the word's internal pattern (`كتاب` → `كتب`, `مدينة` → `مدن`) are not matched by affix stripping. If those matter for your catalogue, add synonyms for your key terms rather than reaching for an aggressive root stemmer that merges unrelated words.

## Mixed Arabic and English queries

Users mix scripts freely, especially for technical and brand terms. A single query might be `افضل laptop للبرمجة`.

**Index both scripts in the same field.** Splitting Arabic and English into separate fields means a mixed query matches neither well.

**Add transliteration aliases.** Users search for `آيفون` and `iPhone` interchangeably. If your catalogue stores only one, the other returns nothing. Store both forms for brand and product names.

**Keep lowercasing in the chain.** It does nothing to Arabic letters but is necessary for the embedded Latin text.

---

## Ranking and relevance

Getting matches is the first half; ordering them sensibly is the second.

**Exact match should outrank stemmed match.** Someone typing an exact product name expects it first. Index an unstemmed sub-field and boost it.

**Weight fields differently.** A title match matters more than a description match.

**Handle the empty result.** Typing errors on Arabic keyboards differ from English ones. Fuzzy matching with a small edit distance, plus a "did you mean" suggestion, turns dead ends into results.

**Log queries that return nothing.** It is the most useful search diagnostic you can add: zero-result queries show exactly which normalisation case you are missing and which content users expect but you do not have.

## Testing

Build a test set from real user language, not your own typing:

- The same word with and without diacritics
- Each alef variant of a common term
- `ة` and `ه` word endings
- With and without the definite article and stacked prefixes
- Eastern Arabic and Western digits in the same query
- Mixed Arabic and English in one query
- Common misspellings from your zero-result log

**Automate these as regression tests.** Search configuration is easy to break during an index migration, and the breakage is silent — nothing errors, results just get worse.

## Frequently asked questions

### Why does my Arabic search miss products that are in the catalogue?

Almost always missing normalisation. The query and the stored text use different written forms of the same word — `أ` versus `ا`, `ة` versus `ه`, diacritics versus none, or Eastern versus Western digits. Normalise both the index and the query and most "missing" products appear.

### Which characters should an Arabic normaliser change?

At minimum: alef with hamza or madda (`أ إ آ`) to bare `ا`, `ة` to `ه`, `ى` to `ي`, and remove diacritics (U+064B–U+065F, U+0670) and tatweel (U+0640). Lucene's Arabic normaliser does exactly this. Converting Eastern Arabic digits to Western digits is a sensible addition.

### Does Elasticsearch's Arabic stemmer reduce words to their root?

No. It is a light stemmer: it removes attached prefixes such as `و`, `ب` and `ال` and strips common suffixes, so `الكتاب` matches `كتاب`. Broken plurals such as `كتب` are not matched. Use synonyms for key terms where that matters.

### My normaliser deletes Eastern Arabic numbers. Why?

Its diacritics range probably runs from U+064B to U+0670, which also covers the Eastern Arabic digits U+0660–U+0669. Use `[\u064B-\u065F\u0670]` instead, and convert digits explicitly rather than deleting them.

### How do I support mixed Arabic and English queries?

Index both scripts in the same field, keep lowercasing in the filter chain for the Latin part, and store transliteration aliases for brand and product names so `آيفون` and `iPhone` both match.

### Is PostgreSQL full-text search good enough for Arabic?

For moderate catalogues, often yes: it includes a Snowball Arabic stemmer and beats `LIKE '%term%'` on both relevance and speed. Plan for diacritics yourself, since the default `unaccent` rules are designed for European accents. Large or search-critical catalogues benefit from a dedicated engine's relevance tuning.

### What is the single most useful thing to add to Arabic search?

A log of queries that return zero results. It shows which normalisation cases you are missing and what content users expect, and it takes a few lines of code.

Normalise both sides, use the engine's Arabic analyser rather than hand-written prefix rules, know where light stemming stops, and log your zero-result queries. That sequence fixes most Arabic search complaints.
