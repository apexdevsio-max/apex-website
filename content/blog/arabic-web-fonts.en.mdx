# Arabic Web Fonts: Performance and Quality Together

To use an Arabic web font without slowing your site: serve it as `woff2`, subset it to the Unicode ranges your content actually uses, load two or three weights at most, set `font-display: swap`, preload only the one font visitors see first, and host it on your own domain. Then give Arabic text more line height than Latin and measure the result instead of guessing.

The reason this needs care is that Arabic fonts are inherently heavier than Latin ones: each letter takes different forms by position (isolated, initial, medial, final), and every form is a separate glyph. The rest of this guide explains each step.

> **Fonts are one layer of localisation.** For the full picture — RTL layout, numerals, dates and content adaptation — see the [complete Arabic localisation guide](/en/blog/arabic-localization-guide). Font loading is one of the performance details we handle in every Arabic build in our [web development services](/en/services/web-development).

## Why are Arabic fonts heavier?

An Arabic letter changes shape depending on its position in a word. The letter «ع» has four forms, and each is a separate glyph in the font file. Add diacritics (vocalisation marks), ligatures, and digits in both the Western and Eastern Arabic sets.

**The practical result:** a complete Arabic font file can be several times the size of a Latin one at the same weight.

---

## 1. File format — the first decision

**Serve `woff2`.** It is the most compressed web font format and is supported in every current browser — see the [MDN `@font-face` documentation](https://developer.mozilla.org/en-US/docs/Web/CSS/@font-face).

```css
@font-face {
  font-family: 'MyArabicFont';
  src: url('/fonts/my-arabic.woff2') format('woff2');
  font-weight: 400;
  font-display: swap;
}
```

**Don't ship `ttf` or `otf` to the browser.** Those are the source formats you subset from; they are larger than `woff2` with no benefit on the web. (Mobile apps are the opposite case: Flutter, for example, bundles TTF or OTF — see [Arabic and RTL in Flutter](/en/blog/flutter-rtl-arabic-guide).)

---

## 2. Ship only the weights you use

**The most common mistake:** loading five weights (thin, regular, medium, bold, black) and using two.

Every weight is a separate file that downloads. **Restrict yourself to two or three:**

- Regular (400) for body text.
- Bold (700) for headings.
- Medium (500) only if you genuinely need it.

**And don't rely on synthesised weights.** Browsers can algorithmically embolden a font that has no bold file, but the result looks worse in Arabic than in Latin. If you use a variable font, one file covers the range — check its size after subsetting against two static weights.

---

## 3. Subsetting — the biggest win

If your pages are in Arabic and English only, there is no reason to ship Cyrillic, Greek or symbol glyphs you never use.

**Subsetting** strips unused glyphs from the font file. Common tools are `pyftsubset` (part of fontTools) and `glyphhanger`.

```bash
pyftsubset my-arabic.ttf \
  --output-file=my-arabic.woff2 \
  --flavor=woff2 \
  --unicodes="U+0600-06FF,U+0750-077F,U+FB50-FDFF,U+FE70-FEFF,U+0020-007E"
```

**The ranges above cover:** basic Arabic, the Arabic Supplement, the two Arabic presentation-form blocks, and basic Latin (for digits and English terms). The [fontTools documentation](https://fonttools.readthedocs.io/en/latest/subset/index.html) notes that `--flavor=woff2` requires the Brotli Python extension. Leave `--layout-features` at its default unless you know what you are removing: the same documentation states that by default "all features required for script shaping are preserved", which is what keeps Arabic letters joining correctly.

> **A warning:** don't over-subset. If you strip glyphs your content uses (names with less common letters, currency symbols, punctuation), empty boxes appear. Test with your real content after every subset.

---

## 4. `font-display` — preventing invisible text

Without a `font-display` value, the strategy is left to the browser, and during a font's "block period" text renders with an invisible fallback — a blank space where your heading should be.

```css
font-display: swap;
```

[MDN describes `swap`](https://developer.mozilla.org/en-US/docs/Web/CSS/@font-face/font-display) as giving the font "an extremely small block period and an infinite swap period": text appears immediately in a fallback font and switches when the custom font arrives. The visitor reads at once, with a brief visual swap.

**To soften the swap:** choose a fallback with similar metrics, and adjust it with `size-adjust`, which MDN documents for overriding a fallback font's metrics to better match the web font:

```css
@font-face {
  font-family: 'ArabicFallback';
  src: local('Tahoma');
  size-adjust: 95%;
}

body {
  font-family: 'MyArabicFont', 'ArabicFallback', sans-serif;
}
```

## 5. Preloading the critical font

The font used in what visitors see first deserves priority:

```html
<link
  rel="preload"
  href="/fonts/my-arabic-regular.woff2"
  as="font"
  type="font/woff2"
  crossorigin
/>
```

**`crossorigin` is required even when the font is on your own domain.** [MDN explains](https://developer.mozilla.org/en-US/docs/Web/HTML/Attributes/rel/preload) that fonts are fetched in anonymous-mode CORS, so the preload must match that mode "even when the fetch is not cross-origin". Without it the preloaded response does not match the font request, and the browser fetches the font a second time.

**Don't preload more than one or two fonts** — every preload competes with your other critical resources.

---

## 6. Line height and vertical space

Arabic needs more vertical room than Latin. The W3C's [Arabic layout requirements](https://www.w3.org/TR/alreq/) put it plainly: Arabic ascenders and descenders extend much further than those of the Latin script. Stacked dots, marks above and below letters, and tall letters such as «ل» and «ك» all need clearance.

**In practice:**

- A `line-height` of 1.4–1.5 that reads comfortably in English feels cramped in Arabic. Start around **1.7–1.8 for body text** and tune by eye with your chosen face.
- Fonts differ: check the same paragraph in each candidate typeface, because a font's own vertical metrics change how much extra room it needs.
- If your content uses diacritics, test them explicitly — marks can collide with the line above at tight line heights.
- Set it on the language, not globally, so English keeps its own rhythm:

```css
:lang(ar) {
  line-height: 1.8;
  letter-spacing: 0;
}
```

## 7. Self-hosting versus third-party services

**Host fonts on your own domain.** The reasons:

- **Faster** — no connection to another domain (DNS, TLS and a request) before text can render.
- **More private** — no visitor data passed to a third party, a real consideration in regulated sectors. See our [PDPL compliance guide](/en/blog/pdpl-compliance-guide).
- **More stable** — no dependence on an external service's availability.

**Check the licence** before self-hosting — some commercial fonts prohibit it or attach conditions.

---

## 8. Choosing the typeface itself

Practical criteria beyond taste:

**Legibility at small sizes.** Many beautiful Arabic fonts become hard to read at 14px. Test at the size you will actually use.

**Weight support.** A single-weight font limits your visual hierarchy.

**Both digit sets** — Western and Eastern Arabic, so either choice renders in the same design.

**Matching Latin glyphs.** Most Arabic content mixes in English terms. A font with harmonised Latin glyphs beats one that leaves the browser to substitute another face.

**Licensing.** Confirm commercial use and self-hosting are permitted.

---

## 9. Measuring — don't guess

After implementing, measure the actual impact:

- **Total font bytes** — in the network panel of your browser's developer tools.
- **Largest Contentful Paint (LCP)** — a heavy or late font delays it.
- **Cumulative Layout Shift (CLS)** — swapping between fallback and custom font can shift content.

Google states that [Core Web Vitals are used by its ranking systems](https://developers.google.com/search/docs/appearance/page-experience), so these numbers matter beyond user experience. **A workable budget** to start from: keep total font bytes for an Arabic site with two weights under about 150KB, and review anything above 300KB.

---

## Common mistakes

**Loading the font from an external service for no reason.** It adds a connection to another domain (DNS, TLS and a request) before text appears, and shares visitor data with a third party. Self-hosting is faster and more private.

**Forgetting `crossorigin` on `preload`.** Fonts are always fetched in CORS mode, so without it the font is downloaded **twice** — once by the preload and once when it is used. The preload then costs bandwidth instead of saving time.

**Loading every weight just in case.** Five weights to use two means wasted files on every visit.

**Over-subsetting.** Removing glyph ranges your content uses produces empty boxes that show up for a user, not for you. Test with real content after each subset.

**Choosing the font from its specimen alone.** Specimens use ideal text at large sizes. Test with your own copy at the size you will use — many fonts lose legibility at 14px.

**Ignoring the default body weight.** If body text is set at 300 (light), Arabic can be hard to read on low-density screens. 400 is the safer weight for long text.

## Frequently asked questions

### Which Arabic font should I choose for a website?

Pick by criteria rather than by name: legibility at your real body size, at least regular and bold weights, both Western and Eastern Arabic digits, harmonised Latin glyphs, and a licence that permits self-hosting and commercial use. Test your shortlist with your own content at actual size before deciding.

### How small can an Arabic font file get?

After subsetting and `woff2` compression, a single weight typically lands in the tens of kilobytes, but the figure depends on the typeface and the ranges you keep. Measure your own file after subsetting rather than relying on a general estimate.

### What line height should Arabic text use?

Start around 1.7 to 1.8 for body text, compared with the 1.4 to 1.5 common in English, and adjust by eye for your typeface. The W3C's Arabic layout requirements note that Arabic ascenders and descenders extend much further than Latin ones, and diacritics need clearance too.

### Should I use one font for Arabic and English?

If one family provides both at consistent quality, yes — simpler and lighter. If you must pair two, make sure their sizes and weights look balanced side by side so mixed text doesn't look disjointed.

### Why does my text appear in a different font briefly?

That is `font-display: swap` working as intended: text shows immediately in a fallback, then switches. Hiding text until the font loads is worse for readers. To soften the switch, choose a metrically similar fallback and tune it with `size-adjust`.

### Do web fonts affect search ranking?

Indirectly. Google says Core Web Vitals are used by its ranking systems, and a heavy or late-loading font can delay Largest Contentful Paint and cause layout shift when it swaps in. Relevance still comes first, so treat fonts as a performance fix, not a ranking strategy.

### What about diacritics and vocalisation marks?

Most Arabic fonts support them, but not all position them equally well. If your content includes tashkeel — religious or educational material — test it explicitly at your chosen line height, since some fonts place marks badly or let them collide with the line above.

## The short version

`woff2`, subset, two or three weights, `swap`, one preload with `crossorigin`, self-hosted — and more line height for Arabic than for Latin. Those decisions cover almost all of the performance and quality gap.
