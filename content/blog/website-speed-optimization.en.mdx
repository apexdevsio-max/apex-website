# Website Speed: A Practical Guide to Core Web Vitals

**A page passes Core Web Vitals when, for 75% of real visits, the main content appears within 2.5 seconds (LCP), the page responds to a tap within 200 milliseconds (INP) and the layout shifts by no more than 0.1 (CLS).** Most sites get there by fixing images, fonts and third-party scripts, in that order, without a rebuild.

This guide is ordered by what usually produces the largest improvement, so you can stop when the numbers pass instead of working through a checklist to the end.

---

## The three metrics that count

| Metric | What it measures | "Good" threshold |
|---|---|---|
| **LCP** — Largest Contentful Paint | How long until the main content appears | 2.5 s or less |
| **INP** — Interaction to Next Paint | How quickly the page responds to a tap or click | 200 ms or less |
| **CLS** — Cumulative Layout Shift | How much the page jumps while loading | 0.1 or less |

The definitions and thresholds are published on [web.dev](https://web.dev/articles/vitals), which recommends measuring them at the **75th percentile** of page loads, separately for mobile and desktop. The set changes over time: INP replaced First Input Delay as the responsiveness metric in 2024.

**How much speed matters for ranking.** Google [states](https://developers.google.com/search/docs/appearance/page-experience) that "Core Web Vitals are used by our ranking systems", but also that "Google Search always seeks to show the most relevant content, even if the page experience is sub-par." A fast page with weak content will not beat a slower page that answers the question better. Fix speed because slow pages lose visitors before they read anything, and treat any ranking benefit as a bonus.

---

## Measure before you change anything

Two kinds of data, and confusing them wastes effort.

**Lab data** — PageSpeed Insights' Lighthouse section, or Lighthouse in Chrome DevTools — runs a simulated load on a simulated device. Use it to diagnose, because it tells you exactly which file or script is slow.

**Field data** — the [Core Web Vitals report in Search Console](https://support.google.com/webmasters/answer/9205520) — comes from the Chrome UX Report, collected from real users visiting your URLs, over a rolling 28-day window. That is what Google uses, and it is what to judge yourself by.

The two often disagree. A site can score well in Lighthouse and still fail in the field because real visitors use older phones and slower networks than the simulation assumes. **Start with field data**, then use lab tools to find the cause. On a new or low-traffic site there may be no field data yet; then lab data is what you have, as an indication rather than a verdict.

## The fixes, in order of typical impact

### 1. Images

On most sites this is the largest single win and the least effort.

The usual failures: a multi-megabyte photograph displayed 400 pixels wide, JPEGs where a modern format would be much smaller, and everything loading at once whether the visitor scrolls that far or not. Google's own figures put [WebP lossy images at 25–34% smaller](https://developers.google.com/speed/webp) than comparable JPEGs at the same quality.

- Serve images at the size they are displayed, not the size they were uploaded.
- Use WebP or AVIF, with a fallback where needed.
- Lazy-load anything below the fold — but **never** the main image, which is usually your LCP element.
- Set explicit width and height so the browser reserves space; this fixes CLS too.

### 2. Fonts

Fonts cause two problems at once: text invisible while loading, and layout shifting when the real font arrives.

- Use `font-display: swap` so text renders immediately in a fallback font.
- Preload the font used in your heading and first paragraph.
- Subset the file to the characters you use — this matters most for Arabic, whose full font files carry many contextual letter forms.
- Limit yourself to two families and the weights you genuinely use.

[Arabic web fonts](/en/blog/arabic-web-fonts) covers subsetting and fallback stacks for Arabic in detail.

### 3. Third-party scripts

This is where sites accumulate weight nobody chose deliberately: an analytics tag, a chat widget, a heatmap tool, two advertising pixels and a cookie banner, each added by someone and none reviewed since.

Third-party scripts are a common cause of poor INP, because they run on the main thread and delay the page's response to taps.

- Audit what actually loads; you will find things nobody remembers adding.
- Remove anything nobody uses.
- Load the rest with `async` or `defer`.
- Delay non-essential scripts until the page is interactive.

### 4. Hosting and delivery

Distance adds latency to every request: a visitor in Riyadh loading from a server in Frankfurt waits for each round trip.

- A CDN puts static files close to your users.
- Caching means repeat visits do not re-download everything.
- Watch server response time (Time to First Byte) in the lab report; a slow server delays everything after it.

Our [hosting comparison](/en/blog/hosting-comparison) covers providers and what to look for.

### 5. JavaScript

The heaviest fix, and the one to reach for last. If the site ships one large JavaScript bundle, splitting it so each page loads only what it needs is real engineering work. It is worth doing when your framework makes it straightforward — and worth asking whether a largely static site needed a heavy client-side framework at all. Our [web development service](/en/services/web-development) builds sites that send server-rendered HTML first and only the JavaScript each page needs.

## What the work involves

| Scope | Effort | Typical outcome |
|---|---|---|
| Quick wins (images, fonts, scripts) | Low — configuration and asset work | Most sites reach passing scores |
| Thorough optimisation (adds hosting, caching, bundle splitting) | Medium — engineering on the existing platform | Comfortable margins; harder pages resolved |
| Rebuild on a different platform | High — a new website project | When the platform itself is the limit |

Most sites never need the third row. If you are being quoted a rebuild to fix speed, ask what the first two rows would achieve first. ## Speed in the Gulf specifically

**Network conditions vary more than averages suggest.** Fast urban 5G coexists with much slower connections. A site tested only on good hardware over good networks will fail part of its real audience, so test with network and CPU throttling switched on.

**Arabic fonts are heavy.** Because Arabic letters take different shapes by position, a full Arabic font file is usually much larger than a Latin one. Subsetting is a requirement here, not a refinement.

**Server location matters for Gulf visitors.** If most of your audience is in the Gulf, serve static files from a CDN with nearby edge locations and choose a hosting region close to them; see the [hosting comparison](/en/blog/hosting-comparison).

## Frequently asked questions

### What LCP, INP and CLS values count as "good"?

LCP of 2.5 seconds or less, INP of 200 milliseconds or less and CLS of 0.1 or less, measured at the 75th percentile of page loads on mobile and desktop separately. A page passes only when all three are in the good range.

### Will a faster site rank higher on Google?

Possibly, but modestly. Google says Core Web Vitals are used by its ranking systems, and also that it shows the most relevant content even when page experience is sub-par. Speed matters most for keeping the visitors you already have.

### Why does my PageSpeed Insights score disagree with Search Console?

PageSpeed Insights shows a lab test from one simulated load, while Search Console shows field data from real Chrome users over the last 28 days. Use the lab test to diagnose and the field data to judge.

### Which fix usually gives the biggest improvement first?

Images: serving them at display size, in WebP or AVIF, with lazy loading below the fold but never on the main image. It is usually both the largest improvement and the least effort.

### Do Arabic sites have particular speed problems?

Yes. Arabic font files are usually much larger than Latin ones, so subsetting to the characters you use is essential. See [Arabic web fonts](/en/blog/arabic-web-fonts) for how to do it without breaking letter joining.

### How long after a fix will Search Console show the improvement?

The report uses a rolling 28-day window of real visits, so expect a full 28 days before a fix is fully reflected and validated. Lab scores change immediately, which makes them useful for checking a fix before the field data catches up.

## Before you spend on a rebuild

Open the Core Web Vitals report in Search Console, note which metric fails on which page group, and work through images, fonts and scripts first. If the numbers still fail after that, the platform may be the constraint — and that is the point to compare a rebuild against continued optimisation.
