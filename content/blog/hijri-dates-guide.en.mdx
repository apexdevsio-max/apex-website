# Hijri Dates in Applications: A Practical Technical Guide

Store every date in Gregorian (UTC) and convert to Hijri only when you display it. For Saudi users, ask for the Umm al-Qura calendar by name — `ar-SA-u-ca-islamic-umalqura` in JavaScript — never the generic `islamic` calendar. Do date arithmetic in Gregorian, show both calendars on appointments and due dates, and in Flutter use a dedicated package because the framework has no Hijri calendar.

Supporting the Hijri calendar is more complex than it looks, and its errors are expensive: an appointment showing the wrong day, a report covering the wrong period, a subscription expiring early. This guide explains each rule with code checked in a current JavaScript runtime.

## Rule one: separate storage from display

This is the most important architectural decision in handling dates.

**Store in Gregorian (UTC)** — in the database, in the API, in logs. The reasons:

- **Arithmetic is simpler** — day differences, ordering and comparisons work without surprises.
- **Compatibility** — databases, libraries and payment systems all assume Gregorian.
- **No ambiguity** — the Hijri calendar has several implementations (see below), so storing a Hijri date means storing an ambiguity.

**Convert to Hijri only in the presentation layer**, according to user preference.

```javascript
// ✅ Store Gregorian, display Hijri
const stored = new Date('2026-08-14T10:00:00Z');   // in the database
const shown = new Intl.DateTimeFormat('ar-SA-u-ca-islamic-umalqura-nu-latn', {
  dateStyle: 'long',
}).format(stored);                                   // "1 ربيع الأول 1448 هـ"

// ❌ Storing Hijri as text
{ date: '1448/03/01' }  // cannot be reliably sorted, differenced or re-interpreted
```

## Rule two: there is no single Hijri calendar

This surprises many developers and is the source of "off by one day" bugs.

The Hijri calendar is lunar, and month starts depend on how the new moon is determined. JavaScript's `Intl` exposes several variants, which [MDN lists](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/supportedValuesOf) as:

| `Intl` calendar | What it is |
|---|---|
| `islamic-umalqura` | Umm al-Qura: KACST-calculated months from 1300 AH to 1600 AH, falling back to `islamic-civil` outside that range |
| `islamic-civil` | Tabular (rule-based) calendar with the civil epoch |
| `islamic-tbla` | Tabular calendar with the astronomical epoch |
| `islamic` | "Unspecified algorithm" — MDN notes it is not known to match any specific real-world variant |

**The difference is real.** Formatting the same day — 14 August 2026 — in Node.js 26:

```javascript
const day = new Date('2026-08-14');
const fmt = (cal) => new Intl.DateTimeFormat(`ar-SA-u-ca-${cal}-nu-latn`,
  { dateStyle: 'long' }).format(day);

fmt('islamic-umalqura'); // "1 ربيع الأول 1448 هـ"
fmt('islamic-civil');    // "29 صفر 1448 هـ"
fmt('islamic');          // "2 ربيع الأول 1448 هـ"
```

Three calendars, three different dates, two of them in different months. **For Saudi users, name `islamic-umalqura` explicitly.** For other markets, confirm with the client or authority which convention their documents follow.

## Conversion in the browser — `Intl` is built in

Most needs are covered by [`Intl.DateTimeFormat`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat) with no library:

```javascript
const date = new Date('2026-08-14');

// Hijri, Eastern Arabic digits
new Intl.DateTimeFormat('ar-SA-u-ca-islamic-umalqura-nu-arab', {
  dateStyle: 'full',
}).format(date);

// Hijri, Western digits
new Intl.DateTimeFormat('ar-SA-u-ca-islamic-umalqura-nu-latn', {
  year: 'numeric', month: 'long', day: 'numeric',
}).format(date);

// Both calendars side by side, with the same digit set
const g = new Intl.DateTimeFormat('ar-SA-u-ca-gregory-nu-latn', { dateStyle: 'long' }).format(date);
const h = new Intl.DateTimeFormat('ar-SA-u-ca-islamic-umalqura-nu-latn', { dateStyle: 'long' }).format(date);
// `${h} (${g})`  →  "1 ربيع الأول 1448 هـ (14 أغسطس 2026)"
```

**Set the calendar and the digits explicitly.** Defaults come from locale data and change between runtimes: in Node.js 26, plain `ar-SA` formats a Gregorian date with Eastern Arabic digits. Leave either one implicit and the output can change under you.

**Test `Intl` output on your real target environments** — older server runtimes and builds with reduced ICU data may lack calendar support.

## Conversion in Flutter

Flutter and Dart's `intl` package have no Hijri calendar, so you need a dedicated package. One example is [`hijri` on pub.dev](https://pub.dev/packages/hijri), whose documentation shows conversion between Gregorian and Umm al-Qura dates:

```dart
import 'package:hijri/hijri_calendar.dart';

HijriCalendar.setLocal('ar');
final h = HijriCalendar.fromDate(DateTime(2026, 8, 14));
print(h.toFormat('dd MMMM yyyy'));
```

**When choosing any Hijri package, verify:**
- Does it implement **Umm al-Qura** rather than a generic calculated calendar?
- What year range does it cover? Table-based implementations are accurate only within their table.
- Is it maintained? Check the last publish date on pub.dev.

**Test with real dates whose correct equivalents you know** — and compare a sample against `Intl`'s `islamic-umalqura` output, especially around month boundaries where errors concentrate.

## Common mistakes

**1. Storing the Hijri date as text.** Prevents sorting, comparison and calculation. Store Gregorian.

**2. Calculating durations in Hijri.** A Hijri month is 29 or 30 days with no fixed pattern. Calculate in Gregorian, then display.

**3. Treating a Hijri year as a Gregorian year.** A Hijri year is 354 or 355 days — 1447 AH ran 355 days in Umm al-Qura — so a "one-year subscription" counted in Hijri is about 11 days shorter.

**4. Ignoring when the day starts.** In some religious contexts the Hijri day begins at sunset, not midnight. Administrative applications use the calendar day; do not assume either for religious features without checking.

**5. Using `islamic` instead of `islamic-umalqura`.** As shown above, the difference can be a day or more.

**6. Mixing digit sets between the two dates.** `ar-SA` and `ar` default to different digits; set `-nu-` on both formatters.

**7. Displaying Hijri only.** Many users think in Gregorian in commercial contexts. Show both calendars on appointments and due dates.

## Product decisions

**Which calendar by default?** For Saudi government-facing and official contexts, Hijri first; in commercial and technical contexts, Gregorian first. **Better: make it a user preference** with a sensible default.

**Dual display.** On appointments, due dates and invoices, show both. It costs nothing and removes ambiguity.

**Financial reports.** State which calendar a period uses — a "first quarter" differs fundamentally between calendars. Put it in the report title, not a footnote.

**Seasons.** Ramadan and Hajj are peak periods for many businesses, and their Gregorian dates move about 11 days earlier each year. If your product is affected, plan from the Hijri dates.

## Frequently asked questions

### Should I store dates in Hijri or Gregorian?

Gregorian (UTC), in the database and the API, converting to Hijri only for display. Storing Hijri prevents reliable sorting and arithmetic and locks in one calendar variant that may not match what you need later.

### What is the difference between `islamic-umalqura` and `islamic` in JavaScript?

`islamic-umalqura` is the Umm al-Qura calendar, which MDN documents as using KACST-calculated months between 1300 and 1600 AH. `islamic` is an unspecified algorithm that MDN says matches no specific real-world variant. In Node.js 26 they render 14 August 2026 as 1 and 2 Rabi al-Awwal 1448 respectively, so always name Umm al-Qura for Saudi users.

### Does JavaScript support the Hijri calendar without a library?

Yes: `Intl.DateTimeFormat` with `ar-SA-u-ca-islamic-umalqura` formats Hijri dates natively. Set the digit set too (`-nu-latn` or `-nu-arab`), and test on your target environments, since builds with reduced ICU data may lack calendar support.

### How do I show Hijri dates in a Flutter app?

Use a dedicated package, because Flutter and Dart's `intl` have no Hijri calendar. The `hijri` package on pub.dev converts between Gregorian and Umm al-Qura dates; check any package's supported year range and compare a sample of its output against known dates.

### How do I calculate the difference between two Hijri dates?

Convert both to Gregorian, calculate there, then display the result. Hijri months are 29 or 30 days with no fixed pattern, so direct Hijri arithmetic is error-prone.

### How much shorter is a Hijri year?

A Hijri year is 354 or 355 days, about 11 days shorter than a Gregorian year. State in your terms which calendar governs a subscription or contract term, and calculate renewal dates in Gregorian internally.

Gregorian in storage, Umm al-Qura by name on screen, explicit digits on every formatter, and both calendars wherever a date carries money or an obligation.
